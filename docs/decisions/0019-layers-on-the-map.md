## From `frontend/src/CLAUDE.md`, line 74

The style segment lives beside the layer's checkbox in the map's **Layers** popover, which is where all five overlay toggles now live: they are the only controls that change what is *looked at* rather than what is *asked for*, which is what earns them a place on the map rather than in the panel (TJ, 2026-08-04). The `Forecast player` switch is a row in that list like the five overlays, and is the one there that draws nothing — it earns its place by answering the same question (#249 review); every row is built by the one `layerRow` in `App.tsx`, so another row cannot be another shape. **Every row is in the list every time** (#460): the player used to be spread in behind `playerAvailable`, so switching the rain radar off took a row out of the MIDDLE of the list and moved every row under it. It now greys instead, which is what the `Forecast grid` row already did and what `CHOICE_ROW`'s `has-[:disabled]:opacity-40` fades on its own. It carries **no `note`**, unlike the grid row, whose `archival data` sentence is older approved copy: a greyed row says it is out of play, and a sentence explaining a control is a tooltip by another name (TJ, 2026-09-22). **The rows are in alphabetical order by label** and a `?raw` test in `styles.test.ts` holds them there: nothing ranks these five against each other — no cost, no severity, no dependency — so any other order is one the reader has to learn. The grid's segment and slider render under the grid's own row rather than after the list, so the order holds whatever is open.

## From `frontend/src/CLAUDE.md`, line 80

The popover hangs off a button **under the search box, top-left**, wearing the same `BUTTON_FLOATING` as Controls: they are the app's only two map buttons, they stack in one column, and a size difference between them read as a mistake rather than a hierarchy. It was first put beneath MapLibre's own zoom/compass/geolocate stack on the right at a measured offset, which clipped the geolocate button: that stack is two control GROUPS with a margin between them, so any offset clearing it is a guess. The left column is the app's own map controls (Controls, search, Layers) and the right is the library's, which is the split worth keeping. Both columns measure off ONE inset: `MAP_EDGE` in `styles.ts` publishes `--map-edge-inset` (12px) on the map wrapper, the app's column and the legend stack read it for their top and left, and `map.css` reads the same property for the vendor stack's own margin — the library ships 10px, which started its buttons a step above the Layers button opposite them. The linter's `style-map-column` check fails an inset spelled at any of those call sites, and `styles.test.ts` does the same for `map.css`, which ESLint does not read. It dismisses on outside `pointerdown` and Escape — `pointerdown` rather than `click` so a press that starts outside dismisses before the map treats it as a gesture. It is the one floating box that is a **menu rather than a key**, so it wears `SURFACE_POPOVER` rather than the legends' `SURFACE_FLOATING`: one step of fill and a heavier shadow, with the border unchanged, because a box the reader acts in must not read as a box the reader only reads. The lighter fill is what `LIFTED_EDGE` exists for — slate-500 carries a well's 3:1 boundary against the panel and only 2.17:1 against this surface, so the segment and the coverage slider inside it take slate-400 instead (`SEGMENT_FLUID_LIFTED`).
