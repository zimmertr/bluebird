## Context

0101 (#643) started a pasted list's forecasts beside the pod's elevation lookup rather than after it, and measured 0.7 s saved out of a run that still took 8.8 s when overpass-api.de was busy, because every row still waited for the lookup before it was assembled. The maintainer's list of 100 Washington summits then landed three times in one evening with every Elevation cell blank (the pod's log: `Custom destination elevation lookup gave up after 8s`, 2026-10-06 at 20:44, 22:26 and 22:28), and asked for the rows to land when the forecasts do, with the elevation and whatever depends on it filled in afterwards, the way the Wildfire column already fills in after the rows.

The first build on PR #674 did that and held the report only when the ranking read a height; the maintainer rejected it on the preview ("looks the same as prod"), because his link ranked by temperature. The second started the lookup at paste time and held nothing, and on an evening when overpass-api.de refused every connection it produced a report in a second with every Elevation cell blank, which he called unacceptable: a forecast at the terrain's height presented as the summit's "lies to the user". He then set three goals, speed, accuracy and never failing, and allowed any architecture that met them.

The hard requirement was unchanged throughout: every forecast number must be read at the destination's elevation, not the terrain's. What makes speed and that requirement compatible is where the elevation enters. Open-Meteo is sent coordinates alone and answers the whole column, 10 m and 2 m plus the five pressure levels; the elevation is read only by the reduce (`weatherMetrics`, `weatherSeries`, `cloudMetrics`, `cloudSeries`), which interpolates the wind and the temperature to it and walks the cloud deck from it. A kept column reduced again at the OSM height produces the same numbers waiting would have, which the test `produces the rows a run that waited would have` in `clientAnalyze.test.ts` holds it to.

What makes never failing possible is a second source that is not a query service. The basemap already draws every summit with its elevation, from OpenFreeMap's vector tiles, and at zoom 14 the `mountain_peak` layer is complete: every OSM peak and volcano node, its elevation in feet rounded from OSM's raw metres (the same arithmetic as the pod's `_ele_ft`), and its OSM node id inside the feature id. Those are static files on a CDN with no query queue in front of them. Measured 2026-10-07 on the 100 Bulgers: 96 placed from 135 tiles (353 KB) in 0.2 to 0.7 s from a warm script, every elevation and every OSM id identical to Overpass's; a 97th, Buck Mountain, by its name 174 m off; two (Raven Ridge, Dorado Needle) are OSM nodes with no `ele`, which no source can place; and one (Reynolds Peak) sits on a node edited after the tile build, which the pod's Overpass lookup finds and the tiles cannot.

## Decision

**The lookup runs as soon as the box holds rows, and it is the only thing in the app that looks an elevation up.** `useElevationLookup` watches the parsed rows and the searched places, and once the box has been still for `LOOKUP_DEBOUNCE_MS` looks up every distinct coordinate the browser has no answer for, one lookup at a time, however the rows got there: a paste, a typed line, a share link opening, an example. The answers (`Identity`: the peak's elevation and OSM id, or that there is none) are kept for the session, so a row is never asked about twice, an added row asks about itself alone and a removed one costs nothing. The pending rows under the box show the elevation as it lands.

**The basemap's tiles answer first, the map server second.** `peakTiles.ts` reads the zoom-14 tile under each row and any neighbour within the match radius (`tilesWithin`), decodes the peak layer itself (`@mapbox/vector-tile` over `pbf`, loaded on the first lookup so the decoder stays off the cold load the Lighthouse gate measures), and applies the pod's own rule: the nearest node within `PEAK_MATCH_RADIUS_M`, mirrored from `CUSTOM_MATCH_RADIUS_M` through `mirrored_constants.json` (row 34), with or without an elevation. It answers only rows placed with an elevation; a row whose nearest node has none, or whose coordinate matches nothing, gets one more try by name within `PEAK_NAME_RADIUS_M` and then goes to the pod, because the pod's null is final where a tile's is as current as the last weekly build. `TILE_CONCURRENCY` is MapLibre's own ceiling on its tile requests (16), so the lookup asks the host for no more at once than the map beside it; the first tile that cannot be read ends the pass and leaves its rows to the pod. The tile URL is the dated path the TileJSON names, so a tile the map already drew is the browser cache's, with the `latest` path as the fallback when the TileJSON cannot be read. Whatever the tiles leave goes to `POST /api/destinations` with `elevation_lookup: true`, the pod's Overpass lookup under its 24 s deadline, 12 s a mirror under 0111's even split. A set the pod gave up on is asked once more after `LOOKUP_RETRY_MS`, tiles and all, and then left until the list changes.

**An analysis never asks the map server and never waits.** It reads what the lookup has learned as it starts (`latest()`), fetches the forecasts for the rows as sent, and makes its one pod call for today's snow depth with every elevation learned so far and `elevation_lookup: false`, a new optional request field (additive, so a minor release). The route answers that call from the pod's snow grid in milliseconds and takes no discovery slot for it: the per-address slot (0103) is now held around a polygon's discovery and a requested lookup alone, by `_overpass_slot` in the route rather than a dependency over the whole request, so the analysis's call never queues behind the same address's lookup still in flight. The one analysis that asks for the lookup is an over-cap list keeping its highest, which cannot choose without every elevation and still waits under `Retrieving elevation…`.

**No report waits for the lookup.** `fetchWeather` and `fetchCloud` take `onColumn`, which hands the caller each raw column as it lands; `reduceWeather` and `reduceCloud`, the reduce the fetch itself runs, are exported so the same arithmetic reduces a kept column again later. `runClientAnalysis` keeps the column of every row whose elevation is unknown, assembles the report at once, and returns the pod call's answer as `late`. `placeRows` is the one placing of an answer on forecast rows, each placed row reduced again from its column at the height returned; the run's `late` and `useAnalyze.placeHeld` both call it, and `placeHeld` is where the lookup's answers land, from the tiles, from the pod and from the retry, on the committed report in place (`useAnalysisReport.patch`) and on the held field a later run reuses. The commit itself applies whatever the lookup learned while the run was fetching, because an answer that landed mid-run reached no report. `pendingHeights` names the committed rows still without an elevation, `patch` narrows it to the rows it did not place, and the table ticks a row's Elevation cell and every cell `heightDependentKey` names (wind, temperature, cloud deck, snow depth) only while the row is also in the lookup's `inquiring` set, the rows it still means to answer; a row given up on stops ticking and reads blank. A ranking on one of those columns reorders once when an answer lands, because `present.ts` re-ranks the patched universe.

**The pod says whether it finished.** `enrich_custom_reporting` adds whether the lookup finished, and the destinations route publishes it as `elevation_lookup_complete`. The browser keeps a null only under `true`; under `false` the rows stay unanswered for the one retry. With `elevation_lookup: false` the flag is true only when no row needed a lookup, the same statement read the same way.

## Alternatives rejected

- Holding the report for the lookup under a ranking on a height-read number, so the table never reorders under the reader. Built first on this PR and rejected by the maintainer on the preview: with Overpass busy it held a temperature ranking for the whole deadline, which is the wait the issue was filed about.
- Splitting the lookup into many small Overpass queries so placed rows land one by one. The slow part is the queue for a slot, not the matching, and overpass-api.de allows two slots per address; the final round shows a 3-row query failing where a 100-row one succeeded.
- Keeping the 8 s deadline. It was set for a reader waiting on an empty screen (#545), and three lists in one evening came back with nothing under it.
- A longer-lived elevation cache on the pod, Open-Meteo's elevation API, and a self-maintained peak index. The first two declined under 0101; the third under #546. The tiles are none of these: they are the map's own data, already drawn beside every summit, maintained by OpenFreeMap.
- Having the pod read the tiles too, for API callers and as the browser's second source. Possible (a point-only tile decoder is small) and not done here: the browser's residual after the tiles is a few rows a list, which is what the pod's Overpass lookup now handles, and an API caller's list keeps the lookup it always had.
- Fetching the forecasts at paste time as well. The Analyze button is a spend boundary (0003) and Open-Meteo's quota is the reader's; the tiles cost no quota, which is why their lookup may run before the click and the forecasts may not.

## Consequences

A pasted summit shows its elevation about a second after the box goes still, with no map server involved, and an analysis's pod call answers in milliseconds. A row the tiles cannot place still shows its precipitation, air quality and freezing level at once and its wind, temperature, cloud deck and snow depth when the pod's lookup answers, ticking meanwhile; a row the pod gives up on twice stops ticking and reads blank, and its wind and temperature are read at Open-Meteo's terrain height for its coordinate, which the maintainer has not accepted as the final answer for those rows. The browser reads one to four tiles a row from `tiles.openfreemap.org`, the same files the map would load zoomed to the point, about 135 tiles and 350 KB for a 100-row list, and a tile edited in OSM reaches a pasted row only through the pod until the next weekly build. The app ships a second copy of a vector-tile decoder (`@mapbox/vector-tile` and `pbf`, both BSD-3-Clause, in `NOTICES.md`), as a chunk loaded on the first lookup. The pod's per-address discovery slot is held for discovery and requested lookups alone, so a request that asks Overpass nothing never queues. A share link that opens with a pasted list sends one lookup on load. A list over the analysis cap sends none.
