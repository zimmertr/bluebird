## Context

Issue #803's reported link drew a 13,825 km² ring with every kind and unnamed peaks. Discovery found 2,613 destinations against the 1,500 cap, and nothing in the browser knew that before the press: the ring was inside the area cap, so the gate had nothing to say. Record 0233 made the refusal visible and a blocker, but only after a press had asked the pod.

The same audit found the spend the browser never priced (D2). The visitor's own address pays Open-Meteo for every forecast, and the free tier allows 5,000 weighted calls an hour. The reported field over two days is 2,613 × (1.6 weather + 1.0 cloud) = 6,794 weighted calls on the forecast host; 1,500 destinations over 30 days is about 8,357 there. Either one paced for nine minutes and then failed on the hourly 429, with the visitor's hour spent. The pod refuses the same thing on its own path (`_check_pacing`, record 0074); the browser did not.

## Decision

- **The ring is counted before Analyze** (`useDestinationCount`), where `/api/capabilities` says `discovery_source: places`, and nowhere else: on Overpass a count would spend a donated service on a ring the reader may never analyze. Once the ring is finished, inside the area cap and has a kind ticked, and has been still for 1.5 s (`COUNT_DEBOUNCE_MS`), the browser posts `/api/destinations` for the ring alone, with no list and `elevation_lookup: false`. Two counts are never closer than 2 s (`COUNT_SPACING_MS`), the destinations bucket's refill interval (30 a minute), so counts cannot drain the bucket the run's own discovery and the coordinates box's lookup draw on. An edit aborts a count in flight; one count runs at a time; answers are kept for the last eight discoveries, so ticking a kind and unticking it again asks nothing.
- **A 200 is the field, and the run forecasts it.** The answer is keyed by `fieldKey` (the ring and the kinds by `discoveryKeys`, and the list by coordinate). A run whose request has the same key takes it in place of discovery, the way a failed run's field is taken (record 0204), and starts at the forecasts. A run carrying a pasted list or a pin has a different key and discovers for itself: the pod merges a list into the ring's field, and the browser has no port of that union.
- **The pod's over-cap 400 is a count.** Its `found` plus the pasted list and the pins is the gate's `overCap`, in the existing sentence (`capDetail`). The pod refuses the union, so this is the number a run would be refused for; a pasted row on a destination the ring also finds counts twice here and once there. Any other answer (429, 502, 503, a dropped connection) is silent and is not asked again for the same ring: the run discovers for itself, and each of those failures already has its message there.
- **The spend is priced before the press, host by host** (`analysisSpend.ts`). The known count (the ring's count plus the list, or the list alone with no ring) is priced the way the browser fetches it, and each call is booked to the host that answers it: the ranking model's weather and cloud column per span (`fetchSpans`), a forecast span on `api.open-meteo.com` and an archive span on `archive-api.open-meteo.com`; air quality over the hours `fetchAqi` asks for (`aqiSpan`) on `air-quality-api.open-meteo.com`; and each compared model's weather for the rows the table shows, on the host of each span. Record 0203 measured the minute bucket per host, and records 0004 and 0203 rest on each service being metered apart. How Open-Meteo counts the hour is unmeasured, so it is assumed to be per host like the minute. When any one host's total is past `limits.open_meteo_hourly_calls`, the gate's `spend` blocker holds Analyze with the existing sentence (`spendDetail`), quoting that host's total rounded up to a whole call. Over the cap, the spend line is not shown: the cap's line already says why, and fixing it changes the count.
- **The run prices itself again** once its field is known and before any forecast (`runClientAnalysis`), host by host as the gate does, on what it would really ask for: the rows with no held forecast, held rows whose air quality is asked again, and the compared models' weather. Past the budget it throws `AnalysisRefusalError(spendDetail(...))`, which record 0233 makes a blocker. This is what holds a deployment with no count.
- **A compare is bounded by the same blocker** (D3), since its models are in the price. The forecast grid now reports a failure when any chunk fails, not only when nothing painted, and its legend says `Unavailable` over whatever did paint, with no new string. That reverses the rule the grid shipped with in #246 (PR #248), carried through #427 and #432, which no record held: there a failure withdrew the layer only when nothing had painted, and the legend's pitch outranked a failure, on the reasoning that a field that drew is still a field. A field that stopped at the hourly quota then looked whole with nothing said, which is the silent failure #803 exists to end.
- **A partial air-quality failure is said** (D5): when one air-quality batch is refused, `fetchAqi` nulls every batch after it. A committed report whose air quality failed for some of its field and not all of it raises `Air quality data is missing for some destinations.` (warn), keyed on its condition, and stays quiet while the existing all-null line speaks.
- **A cleared ring releases a failed run's field** (M7): when the ring is cleared or every kind unticked, the found field record 0204 keeps goes, with its dots and pending rows, and the report on screen stays.
- **The unnamed-peaks toggle counts only with peaks** (M9): `unnamedApplies` gates it in `discoveryKeys`, in the request `planAnalysis` builds and in the refresh check, so a hidden toggle is neither a second discovery of the same question nor a commit cue for a change the reader cannot see.

Record 0203 put the weather host alone at about 4,460 weighted calls at 16 days, inside the hourly 5,000. `analysisSpend.test.ts` holds each of these.

## Alternatives rejected

- **Counting on Overpass too**: it spends a donated service and the destinations bucket on rings nobody analyzes (the issue's option B, bad half).
- **A top-N remedy on the refusal** (option C): the maintainer declined it; `truncateTopElevation` drops rows with no elevation first, which on a mixed set strips most lakes, trailheads and crags.
- **Capping the calendar's span** (D2's other option): it refuses a small analysis that is cheap at any length.
- **One sum across the three hosts**, as the first cut of this change priced it: it held any window of two weeks or less inside the air-quality horizon at about 1,388 destinations, under the candidate cap, on an hourly count nobody has measured and against the per-host metering that was measured.
- **Pricing compared models like the ranking one**, with a cloud column for every destination: `useModelCompare` fetches weather alone, for the shown rows, so that price would block compares that fit.
- **A cross-run hourly ledger** (D3's spend ledger): how Open-Meteo counts the hour is unmeasured (only the minute bucket is, record 0203), so a ledger would be a guess about a window it cannot see. Out of scope for #803.

## Consequences

The gate takes `ringCount` and `spend`; `usePanelMessages` builds both from the count, the list, the window, the compared models and the results cap. `useAnalyze` takes the hourly budget, passes it and the compared-model count to the pipeline, takes `counted` on its options, and returns `dropFound` and `aqiPartial`. The pre-count spends one destinations call per settled ring edit where the places table answers. The hourly budget is assumed per host; if Open-Meteo is measured to count the hour once per address across its hosts, `spendOver` must read `totalCalls` of the host totals instead of the dearest host, and the cap over sixteen days inside the air-quality horizon would then be held. The gate prices the whole field where a re-analysis may reuse held forecasts, so it can hold a run the backstop would allow; which rows a run may reuse is decided at the press.
