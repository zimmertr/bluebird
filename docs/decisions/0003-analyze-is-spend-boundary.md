## From `CLAUDE.md`, line 128

- **Data knobs — polygon, destination types, forecast window, forecast model — keep the explicit commit.** Each is a real fan-out against donated free APIs, and a live-updating calendar drag would 429 the exploring user against their own limit. The forecast window and the forecast model both report themselves through `commitNeeded` (as `window-changed` and `model-changed`): a calendar and a dropdown make changing them a click, so a report can go stale while the panel looks settled (#166, #230). `commitNeeded` reports EVERY reason, not the first, one bullet each; the fixed order leads with `model-changed`, because changing the model can clamp the window as a side effect and leading with the model keeps the clamp attributed to its cause. Three more reasons cover the discovery inputs: `polygon-changed` (a complete ring differing from the analyzed one; silent mid-draw, where the polygon blocker already speaks), `types-changed` (different checked types or unnamed-peaks toggle, independent of the ring cue — two changed inputs are two sentences — and silent without a complete ring, since types with no ring discover nothing), and `destination-added` (a custom destination the analysis never covered, fed by the same `pendingDestinations` set as the map's pending dots). Every cue is warn: the report no longer answers what the panel asks. The discovery identity rides on the analysis snapshot as `polygonKey`/`typesKey` (`discoveryKeys` in `present.ts`, one spelling for both sides) and the comparison is `discoveryChanges` there rather than inline in `App.tsx`, because logic left in `App.tsx` is untestable (it renders the map, and MapLibre cannot run under Vitest) — which is how a since-removed suppression of the types cue shipped uncaught; the weather-only refresh passes the panel's keys explicitly, because its request carries no polygon.

## From `CLAUDE.md`, line 129

- **Presentation knobs — sort, limit and the forecast bounds — apply live, with no fetch.** The browser holds the **full ranked field** before the `limit` cut (`universe` in `useAnalysisReport.ts`, returned by `useAnalyze`), so these are pure re-presentation of held data. `utils/present.ts` is the single derivation (forecast bounds → removals → rank → cut) that every surface reads, so the table, the markers, the legend, and the "showing N of M" count cannot disagree about which rows are displayed. No bound needs a narrowing predicate: nothing knows a destination's precipitation before it is fetched, so a bound can only ever re-read rows already in hand and **loosening one is as live as tightening it**. Each compares the window's worst hour for a ceiling and its best for a floor, so a bound holds for every hour rather than for an average that hides a bad afternoon; precipitation and AQI have no minimum aggregate, so both of their bounds read `precip_total_in` and `aqi_max`, the freezing level is the one family where neither end is the bad one, so its floor reads `freeze_min_ft` and its ceiling `freeze_max_ft`, and snow depth reads `snow_depth_in` at both ends for a third reason — it is today's one number rather than a reduction over hours, so there is no best or worst hour to choose between (#449). Nulls pass, matching the ranking's nulls-last, and for the freezing level that is load bearing rather than tidy: five of the eight models publish none, so a bound that dropped nulls would empty the table under each of them. On the **server** path the bounds ride on the request and the response reports `total_matched` beside `total_queried`, because that path sends only trimmed rows and a matched count cannot be recovered from them; an AQI bound there also promotes the lazy AQI fetch to eager, since a bound on an unfetched value would drop nothing.

## From `CLAUDE.md`, line 131

- **The data snapshot is refined, not broken.** `analyzed` still pins what was *fetched* — the window (as epoch ms), which arm of the selection it came from, and the band the field was discovered under. Live sort and limit re-present that snapshot; they never mutate it. So a re-analysis at a new forecast window still ranks every candidate the analysis saw rather than the handful that survived the last cut.

## From `CLAUDE.md`, line 132

- **A re-analysis reuses the forecasts the browser already holds.** `runClientAnalysis` takes the held field and fetches only the destinations it has no forecast for, so pasting one more destination, ticking unnamed peaks, or stretching the ring buys the delta rather than re-buying the screen. `utils/forecastReuse.ts` owns whether that reuse is legal (identical resolved window and model, inside `FORECAST_REUSE_MS` — 15 min, mirroring the per-location TTL in `cache.py` — with the clock running from the FIRST fetch so a field cannot be kept alive by re-analyzing every fourteen minutes). Because the report is extended rather than rebuilt, **× removals survive**; only a genuine discovery change (polygon, types, CSV) clears them.
