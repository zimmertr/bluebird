# Frontend layout: `src/utils/`

- `src/utils/apiFetch.ts` — the one door to Bluebird Forecast's own API (#381). `fetch` rejects with a `TypeError` before any status exists when the pod cannot be reached, and the browser writes that sentence itself, so six call sites each carrying their own fetch stack meant the error banner could read "Failed to fetch" — a raw exception message, which `docs/STYLES.md` forbids. The translation therefore lives at the primitive rather than at each caller, and the linter's `one-api-door` check pins that **no file under `src/` reaches for `fetch` except this one and `openMeteo.ts`**, beside the two third-party tile doors it exempts (`pointReadout.ts`, `glacierCell.ts`), so the next caller cannot reopen it. What it does not own is the meaning of a status: `apiFetch` returns the `Response` whatever the status came back, because a 429 is a rate-limit flag on the overlays, a refusal body on analyze, and a silent fallback on capabilities. `apiJson` layers the `ok` check and the parse on top for the callers with nothing to say about either, and `postDestinations` is shared because two modules make that one call and neither can own it. An abort passes through untranslated, a cancel being the user's own doing. Every request also has `API_DEADLINE_MS` (110 s) to start answering, after which it is `ApiUnreachable` (#580): past Cloudflare's 100 s on purpose, so in production the edge's 524 still answers a pod that is merely slow and the deadline ends only a request that gets no answer at all; it is a timer on the module's own controller, cleared once the response starts, so a body read never fails in the browser's words. `retryAfterSeconds` reads a 503's or 429's `Retry-After` for the overlays and Open-Meteo, and `overlayFeatures` reads an overlay route's answer. Open-Meteo deliberately keeps its own stack: its taxonomy is a quota, a model domain and a pacer, none of which is about our own pod being up
- `src/utils/abort.ts` — `isAbort`, the one test of a cancel. It reads the name, because in Vitest's jsdom project a real abort is no instance of the global `DOMException`; a `TimeoutError` is a failure. Record: [0194](../../../docs/decisions/0194-a-cancel-is-read-by-its-name.md)
- `src/utils/basemapFailure.ts` — `isStyleFailure`, the one decision behind the basemap's failure note (an `error` before the style has loaded that names no source; sources, tiles, sprites and glyphs are all asked for after `style.load`), and `BASEMAP_FAILED_NOTE`, the approved sentence `panelMessages.ts` shows (#580). Plain data so it runs under node; `map/basemapWatch.ts` does the listening
- `src/utils/openMeteo.ts` — the browser's Open-Meteo HTTP client: the weighted pacer (a port of the backend's `WeightedBudget`, at most 550 weighted calls in any 60 seconds per service, without the backend's shed), the endpoint split (`fetchSpans`), one pool of four open requests per host that every fetch shares, under the five Open-Meteo admits (a `concurrency` 429 is asked once more a second later, booked once), the requests, and `windDirectionSeries`, which is browser-only and so stays out of the pinned port. `fetchWeather` and `fetchCloud` take `onColumn`, which hands a caller each raw column as it lands (#643, #673): Open-Meteo is never sent an elevation, so the requests leave at once, every row is reduced at what is known, and `reduceWeather`/`reduceCloud`, the one reduce the fetch itself runs, let the caller reduce a kept column again at the height a lookup returns, caching it under that height. The reduce reports the height it read at as `terrain_ft` when it was the terrain's rather than the place's own (whole feet, null otherwise), which is what the table's marked Elevation cell shows (Record: [0116](../../../docs/decisions/0116-no-recorded-elevation-shows-terrain-height-marked.md)). A place with no elevation skips the cache read while a column is wanted, because a cached row has no column to hand over. Record: [0114](../../../docs/decisions/0114-report-lands-before-the-elevation-lookup.md) Record: [0075](../../../docs/decisions/0075-pacer-sliding-window.md) Record: [0203](../../../docs/decisions/0203-four-open-requests-per-open-meteo-host.md)
- `src/utils/openMeteoAggregate.ts` — the line-for-line port of `backend/app/services/aggregation.py` and nothing else (#405), pinned to it by `weather_vectors.json` (round-half-even, naive-UTC stamp parsing, zip-vs-series loop asymmetry all deliberate). Its own module so the two halves of the contract read side by side: `openMeteoAggregate.test.ts` reads both files and fails when their functions differ in name or order
- `src/utils/openMeteoErrors.ts` — the Open-Meteo failures the browser tells apart and the sentences they carry (`COVERAGE_PHRASE`, `COVERAGE_MESSAGE_TAIL`, `BAD_BODY_MESSAGE`), the mirror of `backend/app/services/errors.py`. Its own module because both the client and the port throw them, and the client imports the port, so either home would be an import cycle
- `src/utils/clientAnalyze.ts` — ports of the align/assemble/rank helpers in the backend's `services/ranking.py` (the forecast bounds are `constraints.ts`, re-exported here) + the browser-side candidate cap, plus `resolveCustomOnly` (the custom-only path's one server call, a nicety that degrades to unresolved rows on any failure; it asks about EVERY list now, where a list whose rows already knew their elevations used to skip the round trip; snow depth lifted the skip in #449 and left the app in #678, and the skip did not come back, because with no lookup asked for the call answers in milliseconds). No `_merge_custom` port: the server merges on the way in, and a second union here could only disagree with it; returns the trimmed `response` **and** the full ranked `universe`, and owns `refreshEchoRows` (which field a re-analysis re-ranks, and how removals apply to it) beside the two predicates that decide whether an Analyze re-discovers at all (#382): `discoveryBase` spells the user-authored discovery inputs as one string (ring, sorted kinds, unnamed-peaks toggle, parsed CSV rows, and nothing a live knob touches), and `isDiscoveryRefresh` reads a `DiscoveryRecord` against it. That decision is a spend boundary, so both directions are pinned by tests: a matching base whose searched list only SHRANK refreshes weather alone, where a NEW searched place (which must compete against the whole candidate field the echo is not) or any base change buys a fresh discovery. The polygon guard stays in `App.tsx`, because a run with no ring is not a polygon discovery whatever the record says. It also owns `knownTypes`/`withKnownTypes` (#545): `custom_destinations` carries no kind, so every clicked, searched or refreshed row comes back typed `custom`, and these give it the type the browser knows for its coordinate (the held field's, then the place's geocoded kind) before the terrain-height fallback reads it. `resolveCustomOnly` takes whether the pod may look up (`lookup`, the request's `elevation_lookup`, #673): the paste-time lookup says yes, an analysis says no, so its call answers in milliseconds and takes no discovery slot, and the one analysis that says yes is an over-cap list keeping its highest, which cannot choose without every elevation. The pod's call still out when the forecasts land (`resolving`) does not hold the report: the rows are assembled as sent, the raw column of each row with no elevation is kept (`HeldColumns`, by `onColumn`), and the answer comes back on `late` as a `LatePatch`, each changed row reduced again from its column at the height returned (`withWeather`, `withCloud`) with its name and OSM id. `placeRows` is the one placing of an answer on forecast rows, which the run's `late` and `useAnalyze.placeHeld` (the paste-time lookup's answers) both call; a ranking on a height-read number reorders once when an answer lands, through `present.ts` re-ranking the patched universe. Record: [0114](../../../docs/decisions/0114-report-lands-before-the-elevation-lookup.md)

Record: [0176](../../../docs/decisions/0176-places-from-the-planet-and-daily-changes.md) Record: [0204](../../../docs/decisions/0204-a-failed-polygon-run-keeps-its-found-field.md) No React, so its order of events is testable in the node project
- `src/utils/forecastReuse.ts` — whether a held field may stand in for a fresh fetch (`reusableForecasts`: the same resolved window and model, strictly under `FORECAST_REUSE_MS`), and what to hold after a run (`holdForecasts`, which keeps the FIRST fetch's clock so re-analyzing every fourteen minutes cannot keep a field alive). `FORECAST_REUSE_MS` mirrors the pod's per-location TTL (mirror row 21 in the root `CLAUDE.md`). The held field also carries `aqiFailed`, the rows whose air quality FAILED rather than answered null, which `runClientAnalysis` asks again in the same fetch as any new candidates: a failure is never cached by `fetchAqi`, but reuse skipped the fetch for held rows altogether, so an outage stuck to them for the whole reuse window (#580). `fetchAqi` says which nulls are failures (`AqiFetch.failed`), so an answered null is never re-bought. It carries `columns` too, the raw Open-Meteo columns of the held rows whose elevation no lookup has answered, so the next run can reduce them at the height its own lookup returns rather than fetching them again (#673)
- `src/utils/analysisSnapshot.ts` — the `AnalyzedView` a report records (`analyzedView`). Built off the request plus the facts it cannot say (the discovery identity and the compared models), with the window classified once, at commit It also stamps the moment the report committed (`asOfMs`, #696), which the sheet header's `as of` reads, so every committed run sets it, one that reused every forecast included. - `src/utils/analyzeRequest.ts` — which request one Analyze sends (`planAnalysis`), decided without sending it: refresh, discovery, custom-only or nothing, the request each branch builds (a refresh echoes the held field less the removals, #177), the removal scope (`removalScopeFor`, which `App.tsx` also measures once for a link's own ring and list), and when the discovery record is written. - `src/utils/analysisFailure.ts` — which box a failed analysis lands in and the sentence it says: a cancel shows nothing, a refusal goes to the warn box, and the model-coverage sentence is composed here from the picker's label and `COVERAGE_MESSAGE_TAIL`, and whether the Analyze button should offer the run again as `Try again` (`retry` on `RunError`, read by `analyzeGate.retryStands`, #736): every error does except that one, because the same model over the same area fails the same way on a second request and its sentence names a different remedy
- `src/utils/constraints.ts` — the forecast bounds as one value: `Constraints` and `NO_CONSTRAINTS`, the `LOWER_BOUNDS`/`UPPER_BOUNDS` table of which result field each bound compares (the port of `_LOWER_BOUNDS`/`_UPPER_BOUNDS` in the backend's `services/ranking.py`, mirror row 17), the wire conversions both ways, and `filterConstraints`, which `present.ts` runs over the held field. No bound raises a question about a fetch: every analysis fetches the cloud column since #683, which retired `namesOnRequestMetric` and mirror row 29 (`HEIGHT_FAMILIES`, the families read at the destination's height, lives in `metrics.ts` beside the other family lists, #673)
- `src/utils/forecastStore.ts` — the per-location forecast cache, in memory for 15 minutes and across a reload (#337). The in-memory `Map` and its reload snapshot live together, so one module owns both halves of the one cache. A budget rather than a mirror: one entry measures ~10.5 KB and `sessionStorage` holds ~5 MB, so a maximal 1,500-destination analysis (15.7 MB) cannot fit and the newest entries are kept up to `MAX_BYTES`. The stored expiry is wall-clock (`Date.now()` at the write plus the ms remaining), because the in-memory one is a `performance.now()` reading that restarts at zero on reload. Every storage call swallows its failure: a private window, cleared site data, and a full quota all look like an exception from an ordinary property access, and none is a reason to fail an analysis. The snapshot carries the build that wrote it (the entry chunk's URL, which `main.tsx` hands to `keepForecastsAcrossReload` as it hands it to `reloadOnStaleChunk`), because the stored values are aggregates and a release can change what they mean: a snapshot with another build's stamp, or none, is discarded and its key removed, inside the one key the privacy page names rather than in a key per build (#610). Record: [0095](../../../docs/decisions/0095-forecast-snapshot-carries-its-build.md) Measured working: a reload re-ran a 946-destination analysis with **zero** Open-Meteo calls from a 646 KB snapshot

- `src/utils/urlState.ts`: the shareable session as a query string: `encodeState`/`decodeState` over `ShareableState`, pure so the node project checks every param. Both are loops over the table in `urlParams.ts`; what stays here is what no single param owns, the gate that decides whether a state deserves a URL at all, and the query text itself. The writer joins the rows by hand rather than through `URLSearchParams`, so `,` `;` `:` `/` stay readable and a space is `+` (#292); the reader hands a row marked `escaped` its raw text rather than the percent-decoded value. Decoding is tolerant (a malformed value is dropped, the rest of the link still restores) and encoding writes nothing a pristine session has not changed. `decodeAutoAnalyze` reads the one param that is a request rather than state, `analyze=1` (#511): a hand-made link that runs its analysis on open. It is off `ShareableState` on purpose, because that type is what `encodeState` writes and the writer must never emit it, or a link copied after an edit would spend on open. App reads it once at mount and clears it when it fires; the URL writer is what takes it out of the address bar, since while the bar carries it `urlNeedsSync` can never call the bar current, and the fire flushes that queued write
- `src/utils/urlParams.ts`: the codec table, one `{ key, encode, decode }` row per query parameter (#407), in the order a link writes them, since that order is part of every shared link's text. The fourteen forecast bounds and the aggregate dropdowns are rows built by one helper each. A row's `decode` may read what an earlier row decoded (an aggregate param yields to `sort`, `reach` needs a valid `grid`), so the order binds reading too. The window's keys are written by rows but read together by `decodeSelection`, beside them here, because what `h1` means depends on `mode` and `d1`. `escapeQueryText`/`unescapeQueryText` are the one value escape: a space as `+`, the four readable delimiters as themselves, everything else encoded once. Two rows are `escaped` and do their own: `pins` escapes a field's own `,` and `;` and splits the raw text before it decodes each field once, and `customz` writes lz-string's `+` as it is. A `poly` or `pins` coordinate past a pole or the antimeridian drops the ring or the pin, as `view` and `removed` already did, because MapLibre throws on one inside the map's load handler (#622); a pin's OSM id must be `node|way|relation/<digits>` and its kind letters, digits and spaces, or the field is dropped and the pin kept (#621). `customz` is bounded three times, because lz-string inflates with no limit: `MAX_CUSTOMZ_CHARS` before inflating, the published candidate cap times a row's budget after, then the parsed rows against that cap, and a list over any of them is dropped whole. The cap arrives as `decodeState`'s `DecodeLimits`, from `useCapabilities` at mount, rather than as a compiled copy. `sort` and `limit` write only off `DEFAULT_SORT`/`DEFAULT_LIMIT`, which live here beside those rows. Separate so a new param is one row rather than two edits in two long functions that must agree, and so #292's decisions land as row changes. `FIELD_PARAMS` names the params that carry each `ShareableState` field and is typed against every key, so a new field fails the typecheck until a param carries it; `urlParams.test.ts` checks that list against the rows, and pins every key's spelling and order and the decoded answers captured before the table existed (`urlParams.golden.json`). `removed`, `tsort`/`tdesc` and `view` close the table (#292): the ×-removed rows as `lng,lat` pairs at the `geoKey` identity, the header sort only while it differs from the ranking, and the camera, which `encodeState` writes in any link that exists and counts as a reason for one only with `EncodeOptions.cameraMoved`. Record: [0065](../../../docs/decisions/0065-link-carries-camera-removals-order.md)
- `src/utils/urlSync.ts` — whether the address bar needs writing at all, and the trailing debounce over the write. Deliberately not a React effect: the obvious shape, scheduling in an effect and flushing in that effect's cleanup, silently defeats itself, because React runs cleanup on every dependency change rather than only on unmount, so each keystroke flushed the one before it and the burst was never collapsed. Holding the timer in a closure that outlives individual effect runs is what makes the debounce real, and what makes it testable with no DOM
