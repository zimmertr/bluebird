# Frontend layout: `src/utils/`

- `src/utils/apiFetch.ts` — the one door to Bluebird Forecast's own API (#381). `fetch` rejects with a `TypeError` before any status exists when the pod cannot be reached, and the browser writes that sentence itself, so six call sites each carrying their own fetch stack meant the error banner could read "Failed to fetch" — a raw exception message, which `docs/STYLES.md` forbids. The translation therefore lives at the primitive rather than at each caller, and the linter's `one-api-door` check pins that **no file under `src/` reaches for `fetch` except this one and `openMeteo.ts`**, so the next caller cannot reopen it. What it does not own is the meaning of a status: `apiFetch` returns the `Response` whatever the status came back, because a 429 is a rate-limit flag on the overlays, a refusal body on analyze, and a silent fallback on capabilities. `apiJson` layers the `ok` check and the parse on top for the callers with nothing to say about either, and `postDestinations` is shared because two modules make that one call and neither can own it. An abort passes through untranslated, a cancel being the user's own doing. Open-Meteo deliberately keeps its own stack: its taxonomy is a quota, a model domain and a pacer, none of which is about our own pod being up
- `src/utils/openMeteo.ts` — the browser's Open-Meteo HTTP client: the weighted pacer, the endpoint split (`fetchSpans`), the requests, and `windDirectionSeries`, which is browser-only and so stays out of the pinned port
- `src/utils/openMeteoAggregate.ts` — the line-for-line port of `backend/app/services/aggregation.py` and nothing else (#405), pinned to it by `weather_vectors.json` (round-half-even, naive-UTC stamp parsing, zip-vs-series loop asymmetry all deliberate). Its own module so the two halves of the contract read side by side: `openMeteoAggregate.test.ts` reads both files and fails when their functions differ in name or order
- `src/utils/openMeteoErrors.ts` — the Open-Meteo failures the browser tells apart and the sentences they carry (`COVERAGE_PHRASE`, `COVERAGE_MESSAGE_TAIL`, `BAD_BODY_MESSAGE`), the mirror of `backend/app/services/errors.py`. Its own module because both the client and the port throw them, and the client imports the port, so either home would be an import cycle
- `src/utils/clientAnalyze.ts` — ports of the analyze route's align/assemble/rank helpers (the forecast bounds are `constraints.ts`, re-exported here) + the browser-side candidate cap, plus `resolveCustomOnly` (the custom-only path's one server call, a nicety that degrades to unresolved rows on any failure; it asks about EVERY list now, where a list whose rows already knew their elevations used to skip the round trip, because today's snow depth is a second thing only the pod can answer and skipping would leave a pinned summit reading `N/A` beside the same summit inside a drawn ring reading a number — #449). No `_merge_custom` port: the server merges on the way in, and a second union here could only disagree with it; returns the trimmed `response` **and** the full ranked `universe`, and owns `refreshEchoRows` (which field a re-analysis re-ranks, and how removals apply to it) beside the two predicates that decide whether an Analyze re-discovers at all (#382): `discoveryBase` spells the user-authored discovery inputs as one string (ring, sorted kinds, unnamed-peaks toggle, parsed CSV rows, and nothing a live knob touches), and `isDiscoveryRefresh` reads a `DiscoveryRecord` against it. That decision is a spend boundary, so both directions are pinned by tests: a matching base whose searched list only SHRANK refreshes weather alone, where a NEW searched place (which must compete against the whole candidate field the echo is not) or any base change buys a fresh Overpass query. The polygon guard stays in `App.tsx`, because a run with no ring is not a polygon discovery whatever the record says
- `src/utils/analysisPipeline.ts` — one browser analysis from request to report, around `clientAnalyze.ts`: that module fetches, aggregates and ranks a field it is handed, and this one finds the field (`discoverCandidates`: discovery for a ring, resolution for a custom list, and `readErrorBody` for a refused answer), asks `forecastReuse.ts` whether a held field may stand in, shapes each partial field for the screen, and merges the truncation discovery reported with the one the ranking applied (`runAnalysisPipeline`). No React, so its order of events is testable in the node project
- `src/utils/forecastReuse.ts` — whether a held field may stand in for a fresh fetch (`reusableForecasts`: the same resolved window and model, strictly under `FORECAST_REUSE_MS`), and what to hold after a run (`holdForecasts`, which keeps the FIRST fetch's clock so re-analyzing every fourteen minutes cannot keep a field alive). `FORECAST_REUSE_MS` mirrors the pod's per-location TTL (mirror row 21 in the root `CLAUDE.md`)
- `src/utils/analysisSnapshot.ts` — the `AnalyzedView` a report records (`analyzedView`) and whether a request fetches the cloud column (`requestsCloud`). Built off the request plus the facts it cannot say (the discovery identity, the compared models, the snow date its own discovery returned), with the window classified once, at commit
- `src/utils/analyzeRequest.ts` — which request one Analyze sends (`planAnalysis`), decided without sending it: refresh, discovery, custom-only or nothing, the request each branch builds (a refresh echoes the held field less the removals, #177), the removal scope, and when the discovery record is written. Pure, so each branch is testable in the node project; `useAnalyzeCommand.ts` runs the plan
- `src/utils/analysisFailure.ts` — which box a failed analysis lands in and the sentence it says: a cancel shows nothing, a refusal goes to the warn box, and the model-coverage sentence is composed here from the picker's label and `COVERAGE_MESSAGE_TAIL`
- `src/utils/constraints.ts` — the forecast bounds as one value: `Constraints` and `NO_CONSTRAINTS`, the `LOWER_BOUNDS`/`UPPER_BOUNDS` table of which result field each bound compares (the port of `_LOWER_BOUNDS`/`_UPPER_BOUNDS`, mirror row 17), the wire conversions both ways, and `filterConstraints`, which `present.ts` runs over the held field. Apart from `clientAnalyze.ts` because none of it fetches: every bound re-reads rows already in hand, which is what makes it a live knob. `clientAnalyze.ts` re-exports it, so every importer kept its path. It also holds `namesOnRequestMetric` (mirror row 29), the one question a bound can raise about a fetch: whether the ranking or a bound names the cloud column, which an analysis fetches only on request (#117)
- `src/utils/forecastStore.ts` — the per-location forecast cache, in memory for 15 minutes and across a reload (#337). The in-memory `Map` and its reload snapshot live together, so one module owns both halves of the one cache. A budget rather than a mirror: one entry measures ~10.5 KB and `sessionStorage` holds ~5 MB, so a maximal 1,500-destination analysis (15.7 MB) cannot fit and the newest entries are kept up to `MAX_BYTES`. The stored expiry is wall-clock (`Date.now()` at the write plus the ms remaining), because the in-memory one is a `performance.now()` reading that restarts at zero on reload. Every storage call swallows its failure: a private window, cleared site data, and a full quota all look like an exception from an ordinary property access, and none is a reason to fail an analysis. Measured working: a reload re-ran a 946-destination analysis with **zero** Open-Meteo calls from a 646 KB snapshot
- `src/utils/present.ts` — `reportView`, what the displayed report is rendered under (the panel's ranking over the held field's window) and whether it is one hour; and the one derivation from held field + live knobs to displayed rows (`presentResults`, reporting `eligible` and `excluded` so a bound that empties the table is nameable), plus `commitNeeded` (every knob that has stopped applying live, and why: a forecast window that is no longer the one behind the rows, a forecast model that is not the one every held number came from, a changed search ring or type set, a destination the analysis never covered — all that apply, in the fixed order model, window, polygon, types, destination), and `panelCommitCues`, which says which panel state feeds each of those reasons, so the choice App.tsx used to make inline is tested (#409)
- `src/utils/tableColumns.ts` — the column set itself (`COLUMNS`, with an optional `csv` projection where a display formatter would be unparseable) and the one derivation of which columns a report shows (`displayedColumns` = point-sample collapse, then ranked group lifted to the front, then `withModelColumn` inserting **Model** directly after **Name**, the column it qualifies). The table and the CSV export both read it, so a file's columns cannot disagree with the screen's. `applyColumnOrder`/`moveColumn`/`stepColumn` lay the reader's own order over that derivation: it is stored under `bluebird_forecast_view.columnOrder`, it is deliberately NOT in the URL (a shared link opens in the standard order), the CSV follows the screen, and **a change to `Rank by` discards it** — ranking lifts its own metric group to the front and TJ chose to let ranking win (2026-09-14). The discard is guarded by a `rankedOnce` ref in `useTableView`, because the effect that watches `sortBy` also fires on mount and was wiping a stored order on every page load. **Model** is the one column whose default depends on the report (off with one model, on with several, `bluebird_forecast_view.modelColumn` holding a reader's tick once they make one), which is why it is always offered in the Columns picker rather than appearing and vanishing. **Snow depth** is the one column that is not a reading of the window (#449): it is listed in `POINT_LABELS` under the same label it carries in window mode, because that map is also what decides which columns a point sample KEEPS and a metric absent from it disappears from the narrow table
- `src/utils/viewPrefs.ts` — everything one browser remembers about how it reads a report, under `bluebird_forecast_view` and `bluebird_forecast_welcomed` (#382): the results mode an explicit press chose, the column set, the Model column's own answer, the reader's column order, and the welcome flag. Read and write, the way `urlState.ts` splits the URL, and kept apart from it for the reason that split exists: a link is the session someone shares, and these are one browser's habits that no link should carry. One parse per mount rather than the six inline reads `App.tsx` used to carry, each behind its own try/catch and only one of them running the column migration — `columns` predates the wildfire column (#288), `columns2` predates the freezing level (#295) and `columns3` predates snow depth (#449), so each generation migrates with the newer keys added rather than being read verbatim, and the write that supersedes a generation deletes it. Every accessor is total: a storage that refuses (private window, full quota, no `window` at all) yields the defaults, which is the guard the welcome flag was missing. the linter's `app-no-storage` check fails any `localStorage` in `App.tsx`, so a seventh inline read cannot reappear
- `src/utils/columnDrag.ts` — the pure half of dragging a column, shared by the table header and the Columns picker so one gesture means one thing in both (`DRAG_THRESHOLD_PX`, `LONG_PRESS_MS`, `dragBegins`, `keyAtPosition`, `dropEdge`, `ghostLeft`). Here rather than in either component for the usual reason, and `ghostLeft` specifically because the ghost ran off the right edge of a phone before it was measured rather than positioned
- `src/utils/windy.ts` — where a metric cell or a popup row links to on Windy (`windyModel`, `windyTime`, `extremeHourMs`, `windyUrl`). Windy's deep-link grammar is undocumented and was measured against the live site on 2026-09-14; the file's head comment is the record of it, including that the time token is **UTC**, that Windy snaps the hour to the model's own step, and that it ignores an hour in the past. Model tokens were read from Windy's own `W.products` registry and matched by PROVIDER, so a reader who picked the Met Office lands on the Met Office's model; a regional token outside its domain falls back to ECMWF on Windy's side, which is what lets this file carry no coverage polygons. Snow depth is absent from `EXTREME` rather than mapped to a series, because it names no hour at all: the link opens `snowcover` at Windy's own "now" (#449)
- `src/utils/resultsCsv.ts` — the displayed report as a file (`buildResultsCsv`, `csvFilename`). Pure and DOM-free so it is testable under the node-env Vitest; the Blob and anchor live in `utils/exportCsv.ts`. Takes rows already in display order and columns already resolved — it re-derives nothing, because a second answer to "what is on screen" is the bug `present.ts` exists to prevent. A `null` fire map **drops the wildfire column** instead of writing it blank: on screen an empty flag column self-corrects when the ⚠️ arrives a moment later, but a file is read detached from the app, where a column of blanks asserts that every row was checked and cleared. Below the data, a metadata block states the analyzed window as `Forecast start` and `Forecast end` rows, plus one `Forecast end (<model>)` row per compared model that ends inside the window (#493, `CsvOptions.modelEnds`, in the picker's order), so a spreadsheet can compute the hours a short model's plain numbers cover. The mark rides the Model cell (`NOAA HRRR*`, via `isPartialRow`) and never a number, which would turn the column into text (#508), and one row holding `PARTIAL_COVERAGE_NOTE` follows the model rows only when the file carries the Model column and a marked row, because the note explains a mark on that column
- `src/utils/exportCsv.ts` — the report's download (#409): `reportCsv` hands `buildResultsCsv` the table's rows and columns in the order on screen, the analyzed window, the pending rows and the model ends, and sends the wildfire column only when the check answered and the column is shown (the linter's `export-csv-fire-gate`, because a column in a file claims the check ran); `downloadCsv` is the anchor and the object URL, revoked a frame later because Safari cancels a download whose URL is released in the same task. Apart from `resultsCsv.ts` so the formatter stays ignorant of the table's visibility and order rules.
- `src/utils/resultsCells.ts` — what a results-table cell SAYS: the wildfire text and its hover note, the Model column's fallback, the N/A of a metric that declined to answer, the printed value (snow ceiling mark included; a short model's mark is not here but on the Model cell, which `ResultsTableRow.tsx` raises in `TABLE.mark`), a ranked cell's colour, the Windy link, the rank, and the row keys. Apart from `ResultsTableRow.tsx`, which is the markup, so each decision is testable under the node-env Vitest without rendering a table
- `src/utils/forecastWindow.ts` — window normalization twin of `models/analyze.py` (point sample → floored hour + 1 min; horizon checks), plus `windowSource` (which Open-Meteo endpoint answers a window, or that it spans the archive boundary and both do) and `archiveBoundaryMs` (the one instant that seam falls on, mirrored with `limits.py` — #123) and `hourlyStampCount`/`isPointSample`: how many hourly stamps the inclusive filter matched, which is what decides the collapsed table columns instead of a mode name
- `src/utils/calendar.ts` — the forecast window as a calendar (#166), as a barrel over the five flat sibling modules below, so every importer kept its path. Flat rather than a folder, because the linter's `style-one-placement` check globs `src/utils/*.ts` and a folder would escape it. Together they own the servable band, the `ForecastSelection` type (`now` | `days` with optional narrowed `hours`, plus the dateless Dates arm — today outlined, nothing selected, Analyze blocked — that a fresh switch to Dates opens on), month-grid generation, the click/drag reducers, and the conversion to the `datetime-local` pair everything downstream reads. All of it pure, so the node project checks every case without a page and `ForecastCalendar.test.tsx` has only the wiring left to show: the component is wiring only. **The band's far edge is the nearer of two limits, and only one of them is per model.** The hard one is the API's: `FUTURE_LIMIT_DAYS` is 15 (Open-Meteo's "16 days" counts today) and `bandEnd` walks back a further day wherever a local 23:59 lands on the next UTC date, because the request carries UTC dates. The soft one is the selected model's, carried in **hours** rather than days and passed in from `/api/capabilities`. Hours because a model's reach is set by when its last run started, so it lands mid-afternoon as readily as at midnight — rounded down to whole covered days, HRRR's 42 h would offer *today only* anywhere west of Greenwich, which for a short-range mountain model is the same as not offering it. A day the reach lands partway into draws `partial`, the state `DayAvailability` already uses for "we can serve some of this day". `clampSelection` is what a model change does to a window that no longer fits: both ends clamp independently, and it returns `null` for "unchanged" so the panel warns only when something actually moved. `classifyWindow`/`classifyAqiCoverage` read the same band so the grid and the warnings cannot disagree; they sit beside it in `calendarBand.ts`, and `urlState.ts` re-exports them. Both edges now ride in one `BandLimits` object rather than as two number parameters, because 384 hours and 365 days are adjacent arguments of the same type and a transposed pair would compile. The NEAR edge is no longer compiled here at all: it is the archive's reach from `/api/capabilities` (#123), and the days it opens up draw as `full` because the archive holds every hour of them and air quality reaches over them too. It also owns how a window says its own dates: `windowPhrase`/`windowCaption` behind the results header, `snapshotCaption` where a snapshot metric ranks and there is no window to name (`Snow depth as of Sep 22`, #449 — parsed as a LOCAL day, because `Date.parse` reads a bare `YYYY-MM-DD` as UTC midnight and would print the day before west of Greenwich), `archiveSeamPhrase` behind the panel's seam line, and `needsYear` — the one predicate deciding whether a date carries its year (the window's years against the reader's, either end, so both ends carry it or neither does), because a year-old report otherwise reads as four days of `Sat, Sep 13`. Every one of them takes an injectable `now`, so nothing here passes or fails on the year the suite runs in
- `src/utils/calendarDates.ts` — `YYYY-MM-DD` days and `HH:MM` times: parsing, validation (`isValidDatetimeLocal` included, which the URL codec and the classifiers share), and day and month arithmetic through the Date constructor's field overflow, because a local day is 23 or 25 hours on a DST transition. The rest of the calendar reads these rather than doing arithmetic of its own
- `src/utils/calendarBand.ts` — the servable band: `FUTURE_LIMIT_DAYS`, `BandLimits`, `bandStart`/`bandEnd`, `inBand`, the air-quality horizon, and the two classifiers `classifyWindow`/`classifyAqiCoverage` (re-exported by `urlState.ts`, whose suite still tests them). One module, so the grid's unpickable days and the warnings' out-of-range windows are computed by the same functions
- `src/utils/calendarGrid.ts` — the month grid: `monthGrid`'s cells marked `full`/`partial`/`unservable` against the band, `monthHasBandDay` for the month navigation, and the weekday and month labels
- `src/utils/calendarSelection.ts` — `ForecastSelection` and its reducers: a click with a pending anchor, a drag, a clamp to a band that moved under the selection, a switch of arm, and the `datetime-local` pair a selection asks about. Reducers rather than handlers in `ForecastCalendar.tsx`, so the node project pins what a click means
- `src/utils/calendarPhrases.ts` — how a window says its own dates: `windowPhrase`/`windowCaption`, `snapshotCaption`, `archiveSeamPhrase`, and `needsYear`, the one rule for when a date carries its year
- `src/utils/listbox.ts` — the two things the `components/ModelPicker.tsx` popover has to get right and a `<select>` got right for free: where the panel lands (`popoverBox`) and where the arrow keys go (`nextActiveIndex` down the list, `nextToolbarIndex` along the chip row above it — two functions rather than one axis flag, because both are on screen at once and one arrow key may move exactly one of them). Pure, so the node project checks every placement and every key without a page. `popoverBox` clips the trigger's rect into the viewport before measuring from it — the panel is a scrolling column, so a short window puts the trigger below the fold and a raw rect invents room that is not there — and when the content fits neither side it overlaps the trigger to use the whole viewport, so a scrollbar means the screen is too short rather than the gap being too small. It returns the finished `offset` (`{top}` or `{bottom}`) rather than letting the caller re-derive it, which is a bug it already shipped once. It has exactly ONE caller, the hook below, and the linter's `style-one-placement` check fails a second
- `src/utils/modelSelection.ts` — which forecast models the picker has selected and which one of them RANKS, as pure rules (#232). Three invariants every caller leans on: the selected set is never empty, the ranking model is always in it, and `compared` never holds the ranking model, which is what lets the chart treat `compared` as the EXTRA lines beside the report's own. Order is editorial throughout — `/api/capabilities` publishes the models in `MODEL_INFO`'s declaration order, a ranking for mountain terrain rather than a sort — so the chips read in that order however they were selected and a `compare=` link means the same set of patterns whoever built it; an id this deployment does not publish keeps its place at the end rather than being dropped, since a link naming an unknown model is still that reader's link. `toggleSelected` is one row's tick AND a chip's ×, and its one interesting case is unticking the ranking model: the ranking passes to the next chip to the RIGHT, wrapping to the first, because the chips read in editorial order and the right-hand neighbour is the next model the list itself would have offered. `rankWith` is a chip-label tap and deliberately KEEPS the model it replaces selected — the old ranking model is a chip the reader is looking at, and taking it off the chart as a side effect of moving the highlight would remove something they never pointed at. `canRemove` is the last-model rule and `chipFocusAfterRemoval` is where the keyboard lands. It lives here rather than in the component for the reason `listbox.ts` does
- `src/utils/modelCompare.ts` — several models' answers over the charted destinations (#232), the pure half: where a model ends inside the window (`compareEndMs`, and `modelEndLines`/`partialModels`/`isPartialRow`/`PARTIAL_COVERAGE_NOTE` that say so), the blend predicate, the colours, the live/commit predicate (`compareAdded`), the re-index of a fetched series onto the chart's grid (`modelSeriesOnGrid`), and `compareSeries`, which is **one line per (destination, model) pair** — three destinations under three models is nine lines. There is **no cap**: the #232 review removed `MAX_COMPARE_MODELS` because the ceiling hid the control that set it, and the spend is bounded by the Analyze click that buys it. **Every line is solid and COLOUR is the only channel.** A line style for the model is not an option here: `styles.ts` carries no stroke pattern table, and a chart whose point-sample window draws dots could not wear one anyway. **Every (destination, model) pair wears its OWN colour**, because a colour is what identifies a LINE and a model draws one line per destination: colouring by model put two lines of one model on screen in one hue, which is the ambiguity the encoding exists to remove. The pair (destination, RANKING model) keeps the DESTINATION's colour, the hue the marker and the table's checkbox already give it, so a chart with nothing compared draws exactly as it always did. Every other pair takes the next colour from `allocateColors` in `chartColors.ts` the first time it appears and keeps it for the session, however the list changes afterwards. That is the app's ONE allocator and the same one `useChartSelection` hands destinations their colours from: one counter over one palette is what stops a compared line and the destination standing beside it from being handed the same hue. `useChartCompare.ts` computes the pair map during render (allocation is deterministic, so the memo and the effect that persists it agree and no line flashes) and passes it into `useModelCompare`. Nothing else on the chart may pick a hue. The name carries both anyway (`comparedLineLabel` in `chartData.ts`, `1. Mount Rainier (NOAA GFS)`, rank then destination then model on EVERY entry, the ranking model's own lines included — a key that named the destination on one line and the model on the next was the review's second finding). The chart-only legend reads the same pairs (`legendEntries`, #513): one chip per row the table would show in Both (`comparedTableRows ?? results` in `modelRowsFor`'s grouped ranking order, not the table's detail sort, then the pending pseudo-rows), in `rowChartColor`'s colour, labelled `Mount Rainier (NOAA GFS)` while models are compared and by the bare name otherwise. The entry carries the model half as `suffix` (`modelSuffix` in `chartData.ts`, which `modelNamed` and so `comparedLineLabel` compose through) and the chip draws it in a span that never shrinks beside a name span holding the budget the whole label used to have (`max-w-44`), so a long name truncates, the model survives, and a compared chip is wider by exactly its suffix. The chip itself wears `max-w-full`, so on a phone a wide one wraps to its own row and shrinks its name rather than overflowing the legend. A chip's toggle and × still act on the DESTINATION, keyed by `chartKey`, as the table row's do: per-pair hide state would be a second control for what the Models popover already hides, and one the link does not carry. Its React key is `model:` + `pairKey` for a pair, because a destination repeats once per model. The rank is `results`' ranking position, not `tableRows`', which follows a detail sort. A point-sample window draws dots rather than lines, and a dot carries the same colour, so the encoding survives it. `isBlend` reads the `blend` flag `/api/capabilities` publishes per model and never the `_seamless` suffix, which is Open-Meteo's naming habit rather than a contract: a blended product under another name would be drawn as one model with nothing saying otherwise, and a model the server did not publish is not a blend. `useModelCompare` resolves the `analyzed` window through `normalizeWindow` ONCE and uses the result for both the reach test and the fetch, because the snapshot records the request's RAW timestamps: a Current analysis is `start === end`, which unresolved fails every model's reach test and would ask Open-Meteo for a moment between itself and itself. A one-hour comparison draws one point per line. `hooks/useModelCompare.ts` is the spend, and it buys **one single-model `fetchWeather` per model over every charted destination at once, rather than one request naming several models**: a multi-model response collapses to BARE keys the moment any model named in it is out of domain (measured 2026-09-12 at 46.5,8.0, `models=gfs_hrrr,ecmwf_ifs025` answers HTTP 200 with `precipitation` and no suffix, which is one model's numbers under no label), so one model's absence would take its companion's lines with it. The split buys the per-model verdict — a single-model request 400s and names itself — plus the per-location+model cache and the vector-pinned aggregation itself, so a compared line and a re-analysis under that model cannot disagree. **A tick is a data knob and an untick is not.** The fetch is bounded by `analyzed.compareModels`, the set ticked when the analysis committed, so ticking a box afterwards draws nothing and cues `commitNeeded`'s existing `model-changed` reason (`compareAdded` is the predicate, and the asymmetry is the one every live knob has: unticking re-presents numbers already in hand and applies at once). A restored `compare=` link therefore buys its forecasts on the first Analyze and never on load. **Nothing cuts a line to another model's reach** (#493, reversing #232's clamp, which hid the longer models' hours and left the table's ragged aggregates standing anyway). `compareEndMs` is a SPEND decision at the `fetchWeather` call — each model is asked only for the hours it has — and the same instant is what the report states: `useModelCompare` returns `reachEnds` (by model id, only where the end is inside the window) and `endLines` (one per instant for the shown models that drew, grouped by `modelEndLines` so two models with one end share one label), and the chart draws each as a dashed `ReferenceLine` in the axis colour like the Now seam, never red, with no hover entry. `modelRowsFor` copies the end onto a compared row as `coverageEndMs`, and `isPartialRow` reads it: **one mark per row, on the Model cell** (#508, replacing #493's `*` after every weather aggregate, which read as part of a monospace number and put up to twelve marks on one row). The table raises it in a `<sup>` wearing `TABLE.mark`, and the file writes it as `NOAA HRRR*`; every number stays plain on both. `partialModels` reads the short models off the rows on display in the picker's order, one derivation for whether the table shows its footnote (`PARTIAL_COVERAGE_NOTE`, one fixed line that names no model because the marked Model cell does, passed to the memoized table as a string) and the CSV's `Forecast end (<model>)` rows (`CsvOptions.modelEnds`). The footnote follows the Model column on both surfaces: hidden in the Columns picker, the column takes the marks and the note with it. The ranking model never carries it, because the calendar clamps the window to its reach. Only the far end moves, because `forecast_hours` counts hours ahead of now and history is not model-limited. A comparison is a drill-down, not a knob: it never touches `present.ts`, the ranking, the markers or the CSV's numbers (the file's metadata block, where the `Forecast end (<model>)` rows go, is the one place it writes), and it is absent on air quality, which is one model (CAMS) whatever model ranks the field. The chart plots `ChartLine`s rather than rows (`chartData.ts`) for the same reason, and while a comparison is up it receives NO rows at all — the hook composes the ranking model's lines through the same product, so every entry is named and coloured in one place. `components/ModelCompare.tsx` carries NO key: a row of chips naming each model in its colour was built and removed (TJ, #232 review, round four), because the hover box already names rank, destination and model on every entry and the chips listed the models the picker already lists. A failed check (`unavailable`) also reads `N/A` on screen, and the hover text is what separates the two causes: `FIRE_UNCOVERED_NOTE` and `FIRE_UNAVAILABLE_NOTE` in `fireProximity.ts`, the second shared with the panel's footer warning so one failure is never described two ways. Since #203 `unavailable` is rare by construction: the field is measured against the pod's snapshot, which is served past its refresh deadline rather than expiring into nothing, so only a pod that has never once fetched has no answer
- `src/utils/drawControls.ts` — which buttons the Polygon row shows and in what order (#478): Draw/Edit polygon outside the mode, with Clear beside it over a ring; Done, Cancel and Clear inside it at every point count, with Clear disabled at zero the way Done is under three, so the row keeps one shape while points come and go. A module rather than JSX conditions because the row once offered only a disabled Done on entering the mode, which left a phone (no Escape key) with no way out, and a case per state is what keeps that from coming back. The snapshot Cancel restores lives in `useDrawMode` (`drawStartRingRef`, taken when the mode is entered), because every edit is committed to the polygon and the URL as it happens and nothing else holds the old ring
- `src/utils/polygonEdit.ts` — where a click belongs in the ring being drawn (#118). Every new point used to go on the end of the array, which is fine while you are tracing an outline for the first time and wrong the moment the ring is closed: a click on the far side joined it to whichever vertex happened to be last, and the ring crossed itself. Under three points there is still no ring, so the sequence IS the intent and a click appends; from three on it splices into the edge whose DETOUR it adds least to, which is the rule the midpoint handles already follow, so clicking beside a handle and dragging that handle now produce the same ring. Detour rather than perpendicular distance, because a perpendicular can be short while its foot lies off the end of the segment, so a click near one edge's *extension* would beat the edge it is actually beside
- `src/utils/polylabel.ts` — the interior point furthest from any edge (the pole of inaccessibility), which is the coordinate a clicked lake becomes a destination at (#119). A large lake's label is drawn along a line rather than anchored to a point, so the feature carries no coordinate to read off, and the centroid is wrong for exactly the lakes that need one: the centroid of a bent lake sits on the far shore and the centroid of a horseshoe sits on dry land. Mapbox's quadtree search, pruned by each cell's best possible score, so a lake costs a few hundred distance evaluations rather than a scan of its area. `widestPole` runs it per polygon and keeps the roomiest, because a lake arrives as however many pieces of it are currently drawn and concatenating their rings would have the even-odd test read one piece's outline as another's hole
- `src/utils/popupChrome.ts` — the chrome every map popup is built from: the titled header with its link out, the rule under it, the meta band above it, and the `label: value` rows. A string module rather than a component because the result is handed to MapLibre's `setHTML`, which the design system cannot reach: Tailwind scans source for class names and emits CSS for the document, and a string passed to `setHTML` is not a class list that scanner ever sees. So its colours are literals, and they are measured against the white MapLibre draws a popup on rather than against the app's surfaces. The label/value split is COLOUR rather than weight, and that is a measurement rather than a taste: under this markup's `font-family:sans-serif`, Chrome on macOS resolves exactly two faces, so every weight available is either invisible or the title's own. The popup's one `<strong>` therefore stays on the title
- `src/utils/popupRows.ts` — a marker popup's body, derived from the COLUMNS the results table is showing rather than from a list of its own (#370). The popup used to hold six hard-coded rows, so a Current lookup read total, avg, min and max over four copies of one number, and a date-range report showed six of the sixteen values the table had. It groups by metric family, and the unit goes on the heading where every visible column in the group reports in the same one and on each value where they do not — precipitation is the family that splits, its window total being inches and its other three a rate. Pure for the reason `calendar.ts` and `listbox.ts` are: the component is wiring
- `src/utils/resultPopup.ts` — the markup for a ranked destination's popup, opened both by a marker click and by the table's rank click (`focusResult`), so the two can never drift. `popupRows.ts` decides what it says and `popupChrome.ts` how it is framed; what this file adds is the wildfire banner, which is the one table column the popup deliberately does NOT mirror as a row — it is a safety flag rather than a measurement, and a card that said it twice would be worse at saying it once. The whole warning is the link to NIFC's map, because the line is already one statement about one fire
- `src/utils/poiPopup.ts` — the popup a clicked basemap peak or lake opens (#119), wearing the same chrome a ranked result does, because a destination you clicked and the same destination once analyzed are one object at two stages and had drifted into two kinds of card. It shows no forecast: nothing has been fetched for the point yet, and empty metrics would read as a failed lookup rather than an un-run one. Its one button carries the action in a `data-poi-action` value — one attribute for both states — so the map handler reads the intent off the element instead of inferring it from which selector matched
- `src/utils/destinationUrl.ts` — where a row's name links out. A peak goes to Peakbagger's coordinate radius search, whose results are distance-ordered so the row's own peak comes first, rather than its name search, which is ambiguous for common names; everything else deep-links to the exact OSM object the row came from, and a row carrying none (custom and pinned destinations) falls back to an OSM pin at the coordinates
- `src/utils/removals.ts` — what a × captures, and what restoring one has to do. A bare set of coordinate keys hides a row but cannot bring it back: a restore needs the row's name for the list and, because × on a searched place also deregisters it, the `Place` record to re-register. So a removal is a map to both, and `restorePlace` answers which of the two routes back a given entry takes. `authoredScope` is the identity of the user-authored inputs a × was an edit of, so re-authoring that list ends the strikeout's authority over it — and only the live pending preview reads that expiry, because the displayed report and the re-analysis echo are snapshots of one analysis and expiring a removal under them would resurrect a struck-out row mid-typing
- `src/utils/columnResize.ts` — every NUMBER a results-table column width decision needs: the drag clamp, the double-click auto-fit, and the Name column's opening width. Auto-fit is a ceiling on the longest cell and no pad, because any pad made a first double-click WIDEN a column whose header was already its longest content, and a fit has to be idempotent from the natural width onward; its own floor sits deliberately below the drag floor, since a gesture can overshoot into nothing and a fit cannot. Only columns someone has decided are in the map, so the table never needs a seeding pass over every column. The DOM half is `columnMeasure.ts`, and tracking the drag is `useColumnResize`
- `src/utils/columnMeasure.ts` — what a results-table column measures on screen, the DOM half that `columnResize.ts` and `columnDrag.ts` are fed from: a header's content box (`contentWidth`), where each header sits (`headerSpans`), where the insert line goes (`insertLine`), and every cell's width at max-content, restored after (`fitContents`). No React, so each read is testable in jsdom with `placeAt`
- `src/utils/sortResults.ts` — the comparator behind a results-table header click. Two rules beyond a plain compare: nulls sort last in BOTH directions, so a row whose AQI is past its horizon stays at the bottom instead of flipping to the top on a descending sort, and strings collate numerically, so a pasted list numbered 1 to 100 reads in order rather than 1, 10, 100, 2
- `src/utils/unavailableCell.ts` — the `N/A` mark a cell wears when its number is missing for a reason that is NOT the weather, and which columns can wear one (#449). Two metrics can: the freezing level, because five of the eight models publish none (#295), and snow depth, because the destination is outside the SNODAS grid or the pod holds none. Neither is a gap in a series, so neither draws the dash a missing hour gets. One module because three surfaces draw it — the table, the marker popup and the downloaded file — and a file read in a spreadsheet has nothing beside it saying what a blank was supposed to mean. What it does NOT own is the CAUSE, which differs: the freezing level's hover text names the models a reader can switch to, and snow depth carries none, there being no remedy to name (TJ, 2026-09-22). The key list is read off `FAMILY_KEYS`, so an aggregate added to either family cannot be marked in the table and missed here
- `src/utils/snowCeiling.ts` — where the snow depth column stops counting, and the mark a cell wears there (#449). SNODAS carries depth as int16 millimetres, so 32,767 mm is all the file can hold and the header declares it; through the `Meters / 1000` divisor that is `SNOW_DEPTH_CEILING_IN = 1290.04`. The MODEL holds more over deep ice and the file clips it (NOAA's own map service reported 68.62 m at Rainier's summit on 2026-09-16 where the tar read 32.77 m; 86 cells sat on the ceiling on 2026-09-22, Rainier, Baker and Adams among them), so a row there is not a measurement and `snowCellText` prints `≥1,290` rather than the number it was clipped to — ungrouped in the downloaded file, whose other numbers carry no separator. Everything else about the cell is unchanged: its colour band, its Windy link and its rank, which still sorts on the number and ties the ceiling rows together. A sibling of `unavailableCell.ts` rather than part of it, because that module owns the mark for a number that was never AVAILABLE and this one owns the mark for a number that was clipped. The constant is a mirror of `snodas.SNOW_DEPTH_CEILING_IN` pinned by `mirrored_constants.json` (the mark is only honest while both sides agree where the file stops), and the API answers the plain number either way
- `src/utils/freezingLevel.ts` — the freezing level's one asymmetry with every other metric (#295): a cell can be empty because of the MODEL rather than because of the weather, so it wears the `N/A` mark `unavailableCell.ts` owns where a genuinely missing hour draws a dash. Whether a CELL is empty is always read off the data and never off a list, so a model that starts publishing the variable works with no code change. `FREEZE_MODEL_IDS` is the one list, and it exists for the single job the data cannot do: deciding, BEFORE an analysis is bought, whether the models the reader picked can answer the metric they are ranking on. `/api/capabilities` publishes no per-variable flag, so there is nothing to read instead
- `src/utils/analyzeGate.ts` — whether Analyze is enabled, and every reason it is not. The three ways to give it something to do are additive (a drawn polygon with a type checked, a pasted list, a pinned search) and the shared guards veto all of them. `analyzeBlockers` returns EVERY blocker rather than the first: the guards are independent, so a reader with both an oversized polygon and an unservable window used to fix the polygon and be met by a second sentence that had been true the whole time. Its postcondition is that it is non-empty exactly when `canAnalyze` is false, over every combination of the flags including ones the panel cannot produce, so the button can never go dead without saying why. The one exception is mid-analysis, where it returns nothing because the button already says it is busy. Three of its flags are a ranking the selected models cannot answer: `compareAqi`, `compareSnow` (both one source whatever model ranks the field, so a comparison draws one answer once per chip) and `compareFreeze` (five of the eight publish no freezing level). `shouldAutoAnalyze` is the one-shot decision for a link carrying `analyze=1` (#511): the link asked, capabilities have settled, this same gate is open, and it has not fired yet. The gate closes while a run is busy and reopens when it ends, which is why `fired` is part of the question
- `src/utils/panelMessages.ts`: which lines the panel shows under Analyze, and in what order: the run error, the commit cues, the window lines, the blocker sentences, the wildfire line, the refusal and the air-quality gap. A pure function of the panel's derived state, so every line and its condition has a node test, where inside the component none did. It decides only which messages exist; `notices.ts` boxes them and keys their dismissal
- `src/utils/notices.ts` — the footer block's three severity boxes and the dismissal rules behind them (#253). Every message under Analyze is dismissable and each dismisses alone, because the boxes group by severity and never by dismissal. What a dismissal is KEYED to differs by class, and that is the whole design: an event notice keys on its MESSAGE, since each new message is a new fact the reader has not seen, while a derived warning keys on its CONDITION, since the polygon blocker counts down as you draw and a text key would resurface it on every click. One rule gives both the safety and the quiet: a dismissal lives exactly as long as its key stays continuously active, and is pruned the moment it does not
- `src/utils/analyzeOverlay.ts` — the full-screen Analyze overlay, composed from the phase status, the batch counts and the pacer's remaining seconds. The heading carries the TOTAL and never a live fraction, which the bar underneath already draws. Its one detail line is what keeps a paced analysis from reading as a hang — a countdown says the wait is scheduled — and its staged reassurance during discovery is tiered to the measured Overpass mirror behavior rather than to a round number, after the earlier copy promised a ceiling that a large polygon crossed
- `src/utils/customDestinations.ts` — the Custom (CSV) textarea parse: one `Lat,Lon[,Name]` row per line, blank lines and `#` comments skipped, malformed rows dropped. - `src/utils/customList.ts` — the custom side of an analysis as one list: pasted rows ∪ searched places, deduped by `pinKey` (five decimals, ~1 m), with a searched place winning a collision because it carries identity and often an elevation the CSV line lacks. `buildCustomList` re-projects that union down to the wire shape rather than passing it through, so the API contract cannot quietly grow the UI-only fields. `pendingDestinations` is the remainder no analysis has covered, drawn as neutral dots and un-forecasted rows, and it is measured against the custom set the last analysis COVERED rather than against the rows on screen: the rows are the `limit` cut, so keying off them made every addition that ranked below the cut claim it had never been fetched while its forecast sat in the held field (#205)
- `src/utils/urlState.ts`: the shareable session as a query string: `encodeState`/`decodeState` over `ShareableState`, pure so the node project checks every param. Both are loops over the table in `urlParams.ts`; what stays here is what no single param owns, the gate that decides whether a state deserves a URL at all. Decoding is tolerant (a malformed value is dropped, the rest of the link still restores) and encoding writes nothing a pristine session has not changed. `decodeAutoAnalyze` reads the one param that is a request rather than state, `analyze=1` (#511): a hand-made link that runs its analysis on open. - `src/utils/urlParams.ts`: the codec table, one `{ key, encode, decode }` row per query parameter (#407), in the order a link writes them, since that order is part of every shared link's text. The sixteen forecast bounds and the aggregate dropdowns are rows built by one helper each. A row's `decode` may read what an earlier row decoded (an aggregate param yields to `sort`, `reach` needs a valid `grid`), so the order binds reading too. The window's keys are written by rows but read together by `decodeSelection`, beside them here, because what `h1` means depends on `mode` and `d1` and the legacy `at`/`start`/`end` share the answer. - `src/utils/urlSync.ts` — whether the address bar needs writing at all, and the trailing debounce over the write. Deliberately not a React effect: the obvious shape, scheduling in an effect and flushing in that effect's cleanup, silently defeats itself, because React runs cleanup on every dependency change rather than only on unmount, so each keystroke flushed the one before it and the burst was never collapsed.
