# Frontend layout: `src/utils/model/`

- `src/utils/model/modelSelection.ts` — which forecast models the picker has selected and which one of them RANKS, as pure rules (#232). Three invariants every caller leans on: the selected set is never empty, the ranking model is always in it, and `compared` never holds the ranking model, which is what lets the chart treat `compared` as the EXTRA lines beside the report's own. Order is editorial throughout — `/api/capabilities` publishes the models in `MODEL_INFO`'s declaration order, a ranking for mountain terrain rather than a sort — so the chips read in that order however they were selected and a `compare=` link means the same set of patterns whoever built it; an id this deployment does not publish keeps its place at the end rather than being dropped, since a link naming an unknown model is still that reader's link. `toggleSelected` is one row's tick AND a chip's ×, and its one interesting case is unticking the ranking model: the ranking passes to the next chip to the RIGHT, wrapping to the first, because the chips read in editorial order and the right-hand neighbour is the next model the list itself would have offered. `rankWith` is a chip-label tap and deliberately KEEPS the model it replaces selected — the old ranking model is a chip the reader is looking at, and taking it off the chart as a side effect of moving the highlight would remove something they never pointed at. `canRemove` is the last-model rule and `chipFocusAfterRemoval` is where the keyboard lands. It lives here rather than in the component for the reason `listbox.ts` does `comparedInPlay` is the compared models a window puts in play: none on an archive window, which answers one reanalysis whatever model is named, the selection as it stands otherwise (#803, W3). The gate, `useModelCompare` and `useChartCompare` read it, and the selection itself is kept. Record: [0235](../../../../docs/decisions/0235-unanswerable-metric-greys-and-archive-compares-nothing.md)
- `src/utils/model/modelCompare.ts` — several models' answers over the charted destinations (#232), the pure half: where a model ends inside the window (`compareEndMs`, and `modelEndLines`/`partialModels`/`isPartialRow`/`PARTIAL_COVERAGE_NOTE` that say so), the colours, the live/commit predicate (`compareAdded`), the re-index of a fetched series onto the chart's grid (`modelSeriesOnGrid`), and `compareSeries`, which is **one line per (destination, model) pair** — three destinations under three models is nine lines. It takes the ranking model's id and marks that model's pairs `ranked`, so the chart's extreme line can never be set by a compared line (#699). There is **no cap**: the #232 review removed `MAX_COMPARE_MODELS` because the ceiling hid the control that set it, and the spend is bounded by the Analyze click that buys it. **Every line is solid and COLOUR is the only channel.** A line style for the model is not an option here: `styles.ts` carries no stroke pattern table, and a chart whose point-sample window draws dots could not wear one anyway. **Every (destination, model) pair wears its OWN colour**, because a colour is what identifies a LINE and a model draws one line per destination: colouring by model put two lines of one model on screen in one hue, which is the ambiguity the encoding exists to remove. The pair (destination, RANKING model) keeps the DESTINATION's colour, the hue the marker and the table's checkbox already give it, so a chart with nothing compared draws exactly as it always did. Every other pair takes the next colour from `allocateColors` in `chartColors.ts` the first time it appears and keeps it for the session, however the list changes afterwards. That is the app's ONE allocator and the same one `useChartSelection` hands destinations their colours from: one counter over one palette is what stops a compared line and the destination standing beside it from being handed the same hue. `useChartCompare.ts` computes the pair map during render (allocation is deterministic, so the memo and the effect that persists it agree and no line flashes) and passes it into `useModelCompare`. Nothing else on the chart may pick a hue. The name carries both anyway (`comparedLineLabel` in `chartData.ts`, `1. Mount Rainier (NOAA GFS)`, rank then destination then model on EVERY entry, the ranking model's own lines included — a key that named the destination on one line and the model on the next was the review's second finding). Record: [0033](../../../../docs/decisions/0033-compare-encoding.md) The chart-only legend reads the same pairs (`legendEntries`, #513): one chip per row the table would show in Both (`comparedTableRows ?? results` in `modelRowsFor`'s grouped ranking order, not the table's detail sort, then the pending pseudo-rows), in `rowChartColor`'s colour, labelled `Mount Rainier (NOAA GFS)` while models are compared and by the bare name otherwise, with the type ahead of the model on a name two places share (#715). The entry carries the model half as `suffix` (`modelSuffix` in `chartData.ts`, which `modelNamed` and so `comparedLineLabel` compose through) and the chip draws it in a span that never shrinks beside a name span holding the budget the whole label used to have (`max-w-44`), so a long name truncates, the model survives, and a compared chip is wider by exactly its suffix. The chip itself wears `max-w-full`, so on a phone a wide one wraps to its own row and shrinks its name rather than overflowing the legend. A chip's toggle and × still act on the DESTINATION, keyed by `chartKey`, as the table row's do: per-pair hide state would be a second control for what the Models popover already hides, and one the link does not carry. Its React key is `model:` + `pairKey` for a pair, because a destination repeats once per model. The rank is `results`' ranking position, not `tableRows`', which follows a detail sort. A point-sample window draws dots rather than lines, and a dot carries the same colour, so the encoding survives it. `useModelCompare` resolves the `analyzed` window through `normalizeWindow` ONCE and uses the result for both the reach test and the fetch, because the snapshot records the request's RAW timestamps: a Current analysis is `start === end`, which unresolved fails every model's reach test and would ask Open-Meteo for a moment between itself and itself. A one-hour comparison draws one point per line. `hooks/useModelCompare.ts` is the spend, and it buys **one single-model `fetchWeather` per model over every charted destination at once, rather than one request naming several models**: a multi-model response collapses to BARE keys the moment any model named in it is out of domain (measured 2026-09-12 at 46.5,8.0, `models=gfs_hrrr,ecmwf_ifs025` answers HTTP 200 with `precipitation` and no suffix, which is one model's numbers under no label), so one model's absence would take its companion's lines with it. The split buys the per-model verdict — a single-model request 400s and names itself — plus the per-location+model cache and the vector-pinned aggregation itself, so a compared line and a re-analysis under that model cannot disagree. Record: [0032](../../../../docs/decisions/0032-compare-one-fetch-per-model.md) **A tick is a data knob and an untick is not.** The fetch is bounded by `analyzed.compareModels`, the set ticked when the analysis committed, so ticking a box afterwards draws nothing and cues `commitNeeded`'s existing `model-changed` reason (`compareAdded` is the predicate, and the asymmetry is the one every live knob has: unticking re-presents numbers already in hand and applies at once). A restored `compare=` link therefore buys its forecasts on the first Analyze and never on load. **Nothing cuts a line to another model's reach** (#493, reversing #232's clamp, which hid the longer models' hours and left the table's ragged aggregates standing anyway). `compareEndMs` is a SPEND decision at the `fetchWeather` call — each model is asked only for the hours it has — and the same instant is what the report states, floored to the hour the reach falls in because the fetch is stamped in whole hours (#578: unfloored, the mark and the line read 16:11 for data that stops at 16:00), and `endsInsideWindow` compares it with the window's end on the same hourly grid: `useModelCompare` returns `reachEnds` (by model id, only where the end is inside the window) and `endLines` (one per instant for the shown models that drew, grouped by `modelEndLines` so two models with one end share one label), and the chart draws each as a dashed `ReferenceLine` in the axis colour like the Now seam, never red, with no hover entry. `modelRowsFor` copies the end onto a compared row as `coverageEndMs`, and `isPartialRow` reads it: **one mark per row, on the Model cell** (#508, replacing #493's `*` after every weather aggregate, which read as part of a monospace number and put up to twelve marks on one row). The table raises it in a `<sup>` wearing `TABLE.mark`, and the file writes it as `NOAA HRRR*`; every number stays plain on both. `partialModels` reads the short models off the rows on display in the picker's order, one derivation for whether the table shows its footnote (`PARTIAL_COVERAGE_NOTE`, one fixed line that names no model because the marked Model cell does, passed to the memoized table as a string) and the CSV's `Forecast end (<model>)` rows (`CsvOptions.modelEnds`). The footnote follows the Model column on both surfaces: hidden in the Columns picker, the column takes the marks and the note with it. The ranking model never carries it, because the calendar clamps the window to its reach. Only the far end moves, because `forecast_hours` counts hours ahead of now and history is not model-limited. Record: [0058](../../../../docs/decisions/0058-compare-reach-and-mark.md) A comparison is a drill-down, not a knob: it never touches `present.ts`, the ranking, the markers or the CSV's numbers (the file's metadata block, where the `Forecast end (<model>)` rows go, is the one place it writes), and it is absent on air quality, which is one model (CAMS) whatever model ranks the field. The chart plots `ChartLine`s rather than rows (`chartData.ts`) for the same reason, and while a comparison is up it receives NO rows at all — the hook composes the ranking model's lines through the same product, so every entry is named and coloured in one place. `components/ModelCompare.tsx` carries NO key: a row of chips naming each model in its colour was built and removed (TJ, #232 review, round four), because the hover box already names rank, destination and model on every entry and the chips listed the models the picker already lists. What it renders is a note when a compared model drew nothing, and there is no `<select`, no `<button` and nothing that spends — pinned by the linter's `compare-notes-no-control` check, because every control that shapes a comparison belongs in the panel's picker. **Which of those models are DRAWN is the results bar's `Models` link** (`components/ModelsPicker.tsx`, built from `ColumnsPicker`'s parts — same `popoverBox`, same outside-`pointerdown`/Escape dismissal, same `CHOICE_ROW`/`CHOICE_INPUT` rows — because it answers the same kind of question about the same kind of set). It stands under EXACTLY the condition `Columns` does — a bar that gains and loses members is a bar a reader has to look for (#242 review), and one row is a fine answer when one model is selected. Its rows come from the sidebar picker's SELECTION rather than from the chart (`modelRows` in `utils/model/modelVisibility.ts`: ranking model first, then the compared models in the picker's order), so a model ticked before the next Analyze already has a row. **Its rows carry NO colour**, checkbox and label only: a model has no one colour to show, because its lines wear one colour per destination, and a swatch there could only name one of them. The chart's hover box is where a line is identified, by its `1. Mount Rainier (ECMWF IFS)` name and its colour dot. It is PRESENTATION ONLY: the forecasts are bought either way, so hiding must not cancel a fetch and showing must not start one, which is why `hidden` reaches `useModelCompare` as a filter on `shown` and never on `drawnIds`. There is no floor — every box may be unticked, because an empty chart is the honest answer to "hide everything" and a last-one-standing rule is one the reader finds by pressing something that does not respond. It rides in no URL parameter and no storage: a shared link is the comparison that was bought rather than one reader's view of it. `utils/model/modelVisibility.ts` owns the rules (`visibilityRows`, `shownModels`, `toggleHidden`, and `pruneHidden`, which drops the flag of a model that leaves the picker's selection so one picked up again comes back drawn); a hidden model also marks no end and explains no absence, since its lines are missing by instruction
- `src/utils/model/modelVisibility.ts` — which selected models the chart draws (#232), as the `Models` popover's rules: its rows (every model the panel has selected, ranking first, before any fetch), the shown subset, the toggle, and the prune when the panel deselects one. Hiding is presentation alone: the forecasts are already bought, so it spends nothing either way and rides in no link. Out of `ModelsPicker.tsx` so it can be tested
- `src/utils/model/modelDomain.ts` — whether a regional model reaches every place an analysis would forecast (#803, W8): `modelOutsideDomain` names the first model, in `selectedIds`'s order, whose published `domain` (record 0233) leaves a point out, through `fireProximity.pointInOutline`; a model with no domain is never held. `analysisPoints` is the one array of points: a searched ring's vertices, conservative on purpose, then every pasted row and pin, which the found field can join. Record: [0235](../../../../docs/decisions/0235-unanswerable-metric-greys-and-archive-compares-nothing.md)
