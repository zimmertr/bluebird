# Frontend layout: `src/utils/forecastGrid/`

- `src/utils/forecastGrid/forecastGrid.ts` — the forecast grid overlay's pure half (#246), as a barrel over the four sibling modules below, so every importer reads one name. The linter's `grid-layer-hook` check holds how `useGridLayer` wires the overlay (and `app-grid-gate` the Layers row `LayersPopover.tsx` keeps), and `forecastGrid.test.ts` keeps the `?raw` checks on how the map does. Together they own the lattice near the analyzed field's destinations (`buildGrid`: a cell exists only within the coverage reach of some destination — the coverage reach is MODEL-RELATIVE (`GRID_REACH_MIN_X = 1` to `GRID_REACH_MAX_X = 4` pitches of the MODEL's grid, `reachKmFor`; default `GRID_REACH_DEFAULT_FRAC = 0.5`, the bar's middle), set by the Layers popover's Coverage slider, stored and shared as a BAR POSITION (`reach=` percent) so one link means the same rings under any model. The km derive from the MODEL pitch, never the coarsened effective pitch — reach that grew with coarsening would keep kept-cells-per-destination constant and the cap could never converge on scattered fields. The fetch RATCHETS per analysis (`fetchedRef` in `useForecastGrid`): the lattice is built at the largest reach ever committed, each kept cell carries `distancesKm` to its nearest destination, and `gridView` re-cuts the held field to the displayed reach — live with the thumb, no fetch — so only a commit above the ratchet fetches; a partial fetch stalled behind the pacer says `Waiting` in the legend instead of naming a pitch it does not fully have — the union of disks, never the field's bbox, so one stray destination an ocean away grids as its own small patch instead of stretching one 181 km-pitch rectangle across the Atlantic (PR #288 review); coarsened until the KEPT count fits `MAX_GRID_CELLS = 600` and the VIRTUAL `cols`/`rows` fit `MAX_IMAGE_DIM`, because the raster is a WebGL texture; built from the destinations outward, never by filtering the full bbox lattice, which across a hemisphere is millions of cells. **An array position and a lattice index are different numbers now**: `points`/`cells`/`indices` are parallel sparse arrays, positions are the fetch loop's and `pairCells`' currency, and `spec.indices[pos]` is the virtual row-major index that places a sample in the raster — `GridCell.index` always carries the virtual one, and `gridImageCoordinates` reads the lattice geometry fields rather than the first/last kept cell, which are not corners), the pairing of fetched forecasts back onto their lattice positions (`pairCells`, which takes the INDICES its results belong to so a caller can pair one chunk at a time), the raster (`gridRaster`), its corners (`gridImageCoordinates`), the arrows (`gridArrowFeatures`), and `pitchLabel`. Both drawings, the raster and the arrows, read `fillColor`, and a test asserts they agree — if they scored differently, flipping the segment would look like the forecast had changed. **Two styles over one set of samples** (`GridStyle`, `blocks` | `smooth`, **smooth by default since #460**), which are ONE raster layer under two magnification filters — `raster-resampling` is `nearest` for blocks and `linear` for smooth, so the whole switch is a paint property and there is no second layer to keep in step. Record: [0050](../../../../docs/decisions/0050-one-gradient-everywhere.md) The style segment lives beside the layer's checkbox in the map's **Layers** popover, which is where all five overlay toggles now live: they are the only controls that change what is *looked at* rather than what is *asked for*, which is what earns them a place on the map rather than in the panel (TJ, 2026-08-04). The `Forecast player` switch is a row in that list like the five overlays, and is the one there that draws nothing — it earns its place by answering the same question (#249 review); every row is built by the one `layerRow` in `LayersPopover.tsx`, so another row cannot be another shape. **Every row is in the list every time** (#460): the player used to be spread in behind `playerAvailable`, so switching the rain radar off took a row out of the MIDDLE of the list and moved every row under it. It now greys instead, which is what the `Forecast grid` row already did and what `CHOICE_ROW`'s `has-[:disabled]:opacity-40` fades on its own. It carries **no `note`**, unlike the grid row, whose `archival data` sentence is older approved copy: a greyed row says it is out of play, and a sentence explaining a control is a tooltip by another name (TJ, 2026-09-22). **The rows are in alphabetical order by label** and a `?raw` test in `styles.test.ts` holds them there: nothing ranks these five against each other — no cost, no severity, no dependency — so any other order is one the reader has to learn. The grid's segment and slider render under the grid's own row rather than after the list, so the order holds whatever is open. Record: [0019](../../../../docs/decisions/0019-layers-on-the-map.md) **The map's legend is ONE box**, gaining and losing sections as layers toggle and as the ranking changes, the metric colour key among them (#454; it is not a layer — it explains the marker colours, which exist with every layer off — but it is a section of the same box, because a second box cost a border, a gap and a backdrop on a phone whose map can be 161px tall). Five separate boxes cost ~100px of that before #446, and merging the last two took the stack from 313px to 182px (measured 2026-09-17 at 402px, every layer on). **Every section reads in alphabetical order by the label it RENDERS**, the metric key included (TJ, 2026-09-17), so `Active wildfire` leads and a `Temperature` ranking sorts last where an `AQI` one sorts first; it is `.sort()`ed in `MapLegend.tsx` rather than written in order, because one of the labels is the ranked metric's and no source order can be both. Every section is built by the one `legendSection` in `MapLegend.tsx`, which is what lets them be sorted at all: a key on a single value is a ROW with its swatch on the right, and a key on a SCALE is a strip with `legendRamp.ts`' numbers drawn INSIDE it, along the bottom edge on a scrim. Inside rather than under because a strip and a row of numbers under it is two lines and a strip alone is one, which is 14px a section over two sections (TJ, 2026-09-17); the scrim is what makes the ink measurable, since no single colour clears AA over ramps that run the whole hue circle. **The stack is anchored at the TOP**, under the button that switches the layers it explains, and grows downward on both breakpoints (#249 review): a key belongs where the reader last looked for it, and anchored to the bottom it rode up and down with every panel drag while the last box ended up under the forecast player. The `bottom` offset it still carries is a ceiling on the scroll box rather than an anchor — it stops the stack above the timeline's band and above the sheet's top edge, so no box is ever half under a control — and the overflow therefore leaves through the BOTTOM, which is the edge a scroll can follow. Neither an auto margin on the first child nor `justify-end` may come back: a column pushed to the end edge overflows past its START edge, where content sits at negative coordinates with `scrollTop` pinned at 0 and is **unreachable**, measured at 402x874 with four of five boxes there; the linter's `map-stage-anchors` check fails either pattern. Record: [0048](../../../../docs/decisions/0048-legend-one-box.md) At a desk it is the card under the Legend chip since #714, hanging from the chip row rather than from a measured inset, and the Layers menu opens over it. Record: [0174](../../../../docs/decisions/0174-desk-map-rows.md) At `top-16`, long before, it cut through the Layers button and, rendering later in the DOM, painted over it, so switching a layer on made the layer button unclickable. Nothing hides the legends: they render whenever they have content, and they scroll when the map is too short for them. What was too short is fixed at the cause (#249): on a phone the results are a **sheet standing on the map's bottom edge** rather than a flex sibling shrinking it, so the map keeps the whole column and the sheet rests low enough for the whole stack — 182px measured 2026-09-17 at 402x874, with every layer on and a metric key held — to sit above it, scrolling where it no longer fits. That number was 265 with four layer rows and a six-band key (2026-09-14) and 313 once the snow layer's section joined them; #454 merged the two boxes into one and drew both scale keys as a strip, first with the numbers under it (196) and then with them inside it (182). At 182 the camera padding changes hands as well: a default-height table wants 408px and the reserve now leaves 412, so the table stands at its own default on a 402x874 phone instead of being clamped to 398. Record: [0034](../../../../docs/decisions/0034-phone-sheet-on-map.md) **Re-measure `LEGEND_STACK_PX` when a SECTION joins, not when a band does**: a scale is one line plus its label whatever its band count. `utils/resultsSheet.ts` owns every number that follows from that: the resting map floor the panel clamp takes on a phone (the legend stack, its coarse-pointer inset and the timeline's band, counted whether or not a timeline is on screen, because a map overlay must never resize the results), the sheet's height, and the one lift the whole bottom cluster measures from. **That lift is MEASURED, not derived** (`resolveSheetLift`, fed by a `ResizeObserver` on the sheet in `hooks/useResultsLayout.ts`): adding up a header, its grips and the panel heights is an estimate, and the estimate was 20px long on the header and 16px short on each grip, so the four results states sat 44.5, 44.5, 28.5 and 60.5px clear of the player instead of one number (#249 review). The derived `sheetHeightPx` survives for the two jobs an estimate is right for — the resting reserve the clamp takes and the camera padding — both of which must answer the same before and after a drag. Record: [0035](../../../../docs/decisions/0035-measured-sheet-lift.md) Every offset on this edge is then a STYLE rather than a class, derived in one place: `TRANSPORT_GAP_PX` (44px) is the taller of MapLibre's compact attribution and its scale bar plus the library's own 10px margin on both sides of it, `TRANSPORT_BAND_PX` is that gap plus the bar's own height, and a `?raw` test fails a `bottom-*` spelled in `App.tsx` or `TimelineTransport.tsx` — the legend, the transport, and MapLibre's own bottom corners, which ride up on `--map-corner-lift` in `map.css` (`mapCornerLiftPx`). **Both** corners, at **every** width: the scale bar takes the bottom left and the attribution the bottom right — a corner each rather than the pair stacked in one, which made them as tall as both together — and they ride the results' own height, which lands them in the band between the top of the results and the forecast player above (`TRANSPORT_GAP_PX`), each centred in it by `map.css` reading `--map-corner-band` — a control stands as far from the player as from the results, and exactly where the library would stand it with no player on screen. On a phone the attribution is folded to its (i) the moment it is added: maplibre-gl adds it open and folds it only on the first drag. They are the library's controls, anchored to the container's bottom edge, and the app stands its results on that edge at every width: the attribution is a licence term that cannot be covered, and the scale bar reads against the map rather than against a control. The attribution is **compact on a phone and spelled out at a desk**, switched at the sheet's own breakpoint rather than the library's 640px, which is what the OpenStreetMap attribution guideline allows. The map canvas never changes size on a drag, so the `ResizeObserver` in `MapView` stays the only resize path. A drag hands the height over and the legends scroll again, and far enough closes their box to nothing — the accepted limit of a sheet the reader has chosen to pull over the map, which a double press on a grip undoes with the rest of the default. Desktop keeps the docked panel — `SURFACE_SHEET`/`LAYER.sheet` are the phone branch only and a `?raw` test pins the docked class string — but it takes its MAP FLOOR from the same three constants now (`dockedMapFloorPx`): a docked panel covers nothing, yet its bar and grips come out of the map's own column, and the fixed 280 it replaced is older than the legend stack and under half of what the stack needs.
- `src/utils/forecastGrid/forecastGridLattice.ts` — the lattice and everything that decides its pitch: the `GridSpec`/`GridCell` types, the cell cap, the reach, the texture bound, `modelPitchKm` (a model's published finest grid, or the fallback), `gridAllowed`, `buildGrid`, `gridView`, `gridImageCoordinates`, and `pairCells`, which turns fetched forecasts into grid rows through `assemble`. The pitch is the whole of what the picture claims, so every rule that sets it is in one file
- `src/utils/forecastGrid/forecastGridRaster.ts` — `GridStyle` and `gridRaster`: the kept samples as one RGBA buffer, a pixel per lattice cell, with the smooth style's faded edge and the colour bled into the transparent pixels around it. A buffer rather than a canvas, so Vitest asserts on it without a DOM
- `src/utils/forecastGrid/forecastGridLegend.ts` — the overlay's legend row: `pitchLabel`, and `gridLegendLine`, which picks the pitch or the state standing in for it (`Loading`, `Waiting`, `Unavailable`)
- `src/utils/forecastGrid/forecastGridArrows.ts` — `gridArrowFeatures`: one wind arrow per sampled cell, at its centre, for the timeline's current hour
