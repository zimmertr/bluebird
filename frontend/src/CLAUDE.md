# Frontend layout

Every module under `frontend/src/`: what it owns, and why it is separate. This
file is one half of the module layout that used to sit in the repo root's
[`CLAUDE.md`](../../CLAUDE.md), and it is loaded only when a session touches this
tree. Everything that governs a change to these modules — the design-system rule,
the memoization rule, the Python/TypeScript mirrors table, the interaction model —
stays in that root file. Read it first; this is a directory, not a manual.

**A new source module gets a bullet here, in the same PR that adds it.** The bullet says what the module OWNS and why it is separate, at the density of the ones around it; one line is a fine answer for a twenty-line module. Nothing enforces this. A session reads this list before it writes code, so a module named nowhere here is one the next session rediscovers and re-decides (#392).

- `src/components/ForecastCalendar.tsx` — the whole forecast window in one card: a **When** segment picking Current or Dates, an **Hours** segment under it, and the month grid below both. The two segments sit above the grid rather than around it, so the two decisions the window needs read as one block and neither lands below the fold; the grid and the Hours row appear only under Dates, the way the hour fields appear only under Hourly, because Current takes no input at all. "Dates" names the second arm rather than Days or Range because it must be silent about count *and* tense: 55 of the 71 days it reaches are behind today (#234). Holds no date logic of its own (see `utils/calendar.ts`); a mouse drags a range, a finger taps twice, and the selection commits on pointerup so a drag never re-renders the panel per pointermove. Cell brightness is one channel carrying one meaning — **how much of that day the app can serve** (`DayAvailability`) — which is why an adjacent month's days are drawn blank rather than dimmed
- `src/components/SearchBox.tsx` — floating map search (Nominatim place lookup + local coordinate parsing; Enter-to-search only, per Nominatim's no-autocomplete policy)
- `src/components/ResultsTable.tsx` — sortable results table, and *only* the rendering of one: it receives its rows already in display order. Every header CLICK sorts the rows on screen in place and nothing more — the panel's Ranking control is the only thing that re-ranks the field, reorders the column groups, or moves the shading (#242 review). The display order is `App.tsx` state (`detailSort`) so the CSV export can leave in it. A header DRAG is the one other thing a header does, and it moves the column rather than the rows (see `columnDrag.ts`); the two are told apart by distance and by hold, never by which of them fired first, because a tap must still sort. Both the drag listeners and the resize listeners live on `document` rather than on the `th`: a drag leaves the cell it started in on its first frame
- `src/hooks/useAnalyze.ts` — analysis orchestration: candidates via `POST /api/destinations` (discovery for a polygon, resolution for a custom list, both in the one call), then browser Open-Meteo fetches. The one path since #240: an unreachable Open-Meteo fails the analysis with its own message rather than rerouting through the server's shared quota
- `src/utils/apiFetch.ts` — the one door to Bluebird Forecast's own API (#381). `fetch` rejects with a `TypeError` before any status exists when the pod cannot be reached, and the browser writes that sentence itself, so six call sites each carrying their own fetch stack meant the error banner could read "Failed to fetch" — a raw exception message, which `docs/STYLES.md` forbids. The translation therefore lives at the primitive rather than at each caller, and `apiFetch.test.ts` pins that **no file under `src/` reaches for `fetch` except this one and `openMeteo.ts`**, so the next caller cannot reopen it. What it does not own is the meaning of a status: `apiFetch` returns the `Response` whatever the status came back, because a 429 is a rate-limit flag on the overlays, a refusal body on analyze, and a silent fallback on capabilities. `apiJson` layers the `ok` check and the parse on top for the callers with nothing to say about either, and `postDestinations` is shared because two modules make that one call and neither can own it. An abort passes through untranslated, a cancel being the user's own doing. Open-Meteo deliberately keeps its own stack: its taxonomy is a quota, a model domain and a pacer, none of which is about our own pod being up
- `src/utils/openMeteo.ts` — browser Open-Meteo fetch + the aggregation ports of `weather.py`/`air_quality.py`, pinned to the backend by `weather_vectors.json` (round-half-even, naive-UTC stamp parsing, zip-vs-series loop asymmetry all deliberate)
- `src/utils/clientAnalyze.ts` — ports of the analyze route's align/assemble/rank/filter-constraints helpers (`Constraints` and its bound table live here, beside the port, and `present.ts` imports both) + the browser-side candidate cap, plus `resolveCustomOnly` (the custom-only path's one server call, a nicety that degrades to unresolved rows on any failure). No `_merge_custom` port: the server merges on the way in, and a second union here could only disagree with it; returns the trimmed `response` **and** the full ranked `universe`, and owns `refreshEchoRows` (which field a re-analysis re-ranks, and how removals apply to it) beside the two predicates that decide whether an Analyze re-discovers at all (#382): `discoveryBase` spells the user-authored discovery inputs as one string (ring, sorted kinds, unnamed-peaks toggle, parsed CSV rows, and nothing a live knob touches), and `isDiscoveryRefresh` reads a `DiscoveryRecord` against it. That decision is a spend boundary, so both directions are pinned by tests: a matching base whose searched list only SHRANK refreshes weather alone, where a NEW searched place (which must compete against the whole candidate field the echo is not) or any base change buys a fresh Overpass query. The polygon guard stays in `App.tsx`, because a run with no ring is not a polygon discovery whatever the record says
- `src/utils/forecastStore.ts` — the per-location forecast cache across a reload (#337). A budget rather than a mirror: one entry measures ~10.5 KB and `sessionStorage` holds ~5 MB, so a maximal 1,500-destination analysis (15.7 MB) cannot fit and the newest entries are kept up to `MAX_BYTES`. The stored expiry is wall-clock (`Date.now()` at the write plus the ms remaining), because the in-memory one is a `performance.now()` reading that restarts at zero on reload. Every storage call swallows its failure: a private window, cleared site data, and a full quota all look like an exception from an ordinary property access, and none is a reason to fail an analysis. Measured working: a reload re-ran a 946-destination analysis with **zero** Open-Meteo calls from a 646 KB snapshot
- `src/utils/present.ts` — the one derivation from held field + live knobs to displayed rows (`presentResults`, reporting `eligible` and `excluded` so a bound that empties the table is nameable), plus `commitNeeded` (every knob that has stopped applying live, and why: a forecast window that is no longer the one behind the rows, a forecast model that is not the one every held number came from, a changed search ring or type set, a destination the analysis never covered — all that apply, in the fixed order model, window, polygon, types, destination)
- `src/utils/tableColumns.ts` — the column set itself (`COLUMNS`, with an optional `csv` projection where a display formatter would be unparseable) and the one derivation of which columns a report shows (`displayedColumns` = point-sample collapse, then ranked group lifted to the front, then `withModelColumn` inserting **Model** directly after **Name**, the column it qualifies). The table and the CSV export both read it, so a file's columns cannot disagree with the screen's. `applyColumnOrder`/`moveColumn`/`stepColumn` lay the reader's own order over that derivation: it is stored under `bluebird_forecast_view.columnOrder`, it is deliberately NOT in the URL (a shared link opens in the standard order), the CSV follows the screen, and **a change to `Rank by` discards it** — ranking lifts its own metric group to the front and TJ chose to let ranking win (2026-09-14). The discard is guarded by a `rankedOnce` ref in `App.tsx`, because the effect that watches `sortBy` also fires on mount and was wiping a stored order on every page load. **Model** is the one column whose default depends on the report (off with one model, on with several, `bluebird_forecast_view.modelColumn` holding a reader's tick once they make one), which is why it is always offered in the Columns picker rather than appearing and vanishing
- `src/utils/viewPrefs.ts` — everything one browser remembers about how it reads a report, under `bluebird_forecast_view` and `bluebird_forecast_welcomed` (#382): the results mode an explicit press chose, the column set, the Model column's own answer, the reader's column order, and the welcome flag. Read and write, the way `urlState.ts` splits the URL, and kept apart from it for the reason that split exists: a link is the session someone shares, and these are one browser's habits that no link should carry. One parse per mount rather than the six inline reads `App.tsx` used to carry, each behind its own try/catch and only one of them running the column migration — `columns` predates the wildfire column (#288) and `columns2` predates the freezing level (#295), so each generation migrates with the newer keys added rather than being read verbatim, and the write that supersedes a generation deletes it. Every accessor is total: a storage that refuses (private window, full quota, no `window` at all) yields the defaults, which is the guard the welcome flag was missing. `viewPrefs.test.ts` fails any `localStorage` in `App.tsx`, so a seventh inline read cannot reappear
- `src/utils/columnDrag.ts` — the pure half of dragging a column, shared by the table header and the Columns picker so one gesture means one thing in both (`DRAG_THRESHOLD_PX`, `LONG_PRESS_MS`, `dragBegins`, `keyAtPosition`, `dropEdge`, `ghostLeft`). Here rather than in either component for the usual reason, and `ghostLeft` specifically because the ghost ran off the right edge of a phone before it was measured rather than positioned
- `src/utils/windy.ts` — where a metric cell or a popup row links to on Windy (`windyModel`, `windyTime`, `extremeHourMs`, `windyUrl`). Windy's deep-link grammar is undocumented and was measured against the live site on 2026-09-14; the file's head comment is the record of it, including that the time token is **UTC**, that Windy snaps the hour to the model's own step, and that it ignores an hour in the past. Model tokens were read from Windy's own `W.products` registry and matched by PROVIDER, so a reader who picked the Met Office lands on the Met Office's model; a regional token outside its domain falls back to ECMWF on Windy's side, which is what lets this file carry no coverage polygons
- `src/utils/resultsCsv.ts` — the displayed report as a file (`buildResultsCsv`, `csvFilename`). Pure and DOM-free so it is testable under the node-env Vitest; the Blob and anchor live in `App.tsx`. Takes rows already in display order and columns already resolved — it re-derives nothing, because a second answer to "what is on screen" is the bug `present.ts` exists to prevent. A `null` fire map **drops the wildfire column** instead of writing it blank: on screen an empty flag column self-corrects when the ⚠️ arrives a moment later, but a file is read detached from the app, where a column of blanks asserts that every row was checked and cleared
- `src/utils/forecastWindow.ts` — window normalization twin of `models.py` (point sample → floored hour + 1 min; horizon checks), plus `windowSource` (which Open-Meteo endpoint answers a window, or that it spans the archive boundary and both do) and `archiveBoundaryMs` (the one instant that seam falls on, mirrored with `models.py` — #123) and `hourlyStampCount`/`isPointSample`: how many hourly stamps the inclusive filter matched, which is what decides the collapsed table columns instead of a mode name
- `src/utils/calendar.ts` — the forecast window as a calendar (#166): the servable band, the `ForecastSelection` type (`now` | `days` with optional narrowed `hours`, plus the dateless Dates arm — today outlined, nothing selected, Analyze blocked — that a fresh switch to Dates opens on), month-grid generation, the click/drag reducers, and the conversion to the `datetime-local` pair everything downstream reads. All of it pure, because Vitest has no DOM and a `ForecastCalendar.test.tsx` would be silently uncollected — the component is wiring only. **The band's far edge is the nearer of two limits, and only one of them is per model.** The hard one is the API's: `FUTURE_LIMIT_DAYS` is 15 (Open-Meteo's "16 days" counts today) and `bandEnd` walks back a further day wherever a local 23:59 lands on the next UTC date, because the request carries UTC dates. The soft one is the selected model's, carried in **hours** rather than days and passed in from `/api/capabilities`. Hours because a model's reach is set by when its last run started, so it lands mid-afternoon as readily as at midnight — rounded down to whole covered days, HRRR's 42 h would offer *today only* anywhere west of Greenwich, which for a short-range mountain model is the same as not offering it. A day the reach lands partway into draws `partial`, the state `DayAvailability` already uses for "we can serve some of this day". `clampSelection` is what a model change does to a window that no longer fits: both ends clamp independently, and it returns `null` for "unchanged" so the panel warns only when something actually moved. `urlState`'s `classifyWindow`/`classifyAqiCoverage` read the same band so the grid and the warnings cannot disagree. Both edges now ride in one `BandLimits` object rather than as two number parameters, because 384 hours and 365 days are adjacent arguments of the same type and a transposed pair would compile. The NEAR edge is no longer compiled here at all: it is the archive's reach from `/api/capabilities` (#123), and the days it opens up draw as `full` because the archive holds every hour of them and air quality reaches over them too. It also owns how a window says its own dates: `windowPhrase`/`windowCaption` behind the results header, `archiveSeamPhrase` behind the panel's seam line, and `needsYear` — the one predicate deciding whether a date carries its year (the window's years against the reader's, either end, so both ends carry it or neither does), because a year-old report otherwise reads as four days of `Sat, Sep 13`. Every one of them takes an injectable `now`, so nothing here passes or fails on the year the suite runs in
- `src/components/ModelPicker.tsx` — the forecast model as a button opening a listbox of all of them, in the app's one popover shell and placed by the app's one popover hook (see the bullet below), so it is portalled to `document.body` and positioned fixed like every other panel. A native `<select>` cannot do this job: choosing well means reading eight summaries against each other, a select shows one at a time, and its options cannot carry them (the shortest needs 303px of label where the control has 245px). `title` on an option is no way out either — macOS draws the list as an OS menu that renders no tooltip, and a phone has no hover. Fixed rather than absolute because `ControlPanel` is an `overflow-y-auto` column that would clip a child at the scroll boundary. It takes a `disabled` prop for the one window the model does not apply to (an archive window, #123 — a window that CROSSES the boundary keeps the picker, because its forecast half is the chosen model's), wearing `DISABLED` rather than disappearing: a control that vanishes takes its label and its last value with it, and an info line under Analyze says why it is faded (it was a `title` on the trigger until 2026-09-14, out of reach of every touch reader). It is also where the chart's model comparison is chosen (#232), and the popover is **two parts with one gesture each**. **The LIST selects**: tick a row's box or click anywhere on the row, untick to remove, and nothing on a row ranks or closes the popover. **The CHIP ROW above it ranks**, under a `Selected models` header drawn in the list header's own recipe so the popover's two blocks read as two parts of one control: one chip per selected model in the published editorial order (never the order selected), the ranking model's chip highlighted with `CHIP.active`, and a tap on any other chip's label moves the highlight to it — the `model-changed` data knob, window clamp included, with the model it replaces keeping its chip. The split is the design: one row that both selected and ranked put two gestures a few pixels apart, one of which dismissed the list under the reader's hand. A chip's × deselects it; the ranking chip has none, so unticking its ROW is how it goes, and the ranking then passes to the next chip to the right, wrapping to the first. The last selected model cannot be given up — no ×, and its row's box disabled — because a report has to come from some model, and `role="option"` carries `aria-disabled` to say so. Nothing inside the popover closes it: Escape and an outside `pointerdown` only, which is `usePopover`'s rule rather than this file's, so the Columns picker closes the same way by construction. The closed trigger reads `{label} +{n}`, the label ellipsizing rather than widening past `CONTROL_W`, because the count is the only thing on it a reader cannot otherwise see. The listbox is `aria-multiselectable` and `aria-selected` means "on the chart"; the drawn checkboxes are `aria-hidden` with `tabIndex={-1}`, because a focusable input inside a `role="option"` would be a second tab stop in a list whose whole keyboard model is one element plus `aria-activedescendant`, and Enter and Space both toggle the active row. The chip row is a `role="toolbar"` with a roving tabindex: ArrowLeft/ArrowRight/Home/End walk it (`nextToolbarIndex`, the horizontal twin of `nextActiveIndex`, separate so one arrow key moves exactly one of the two parts), Enter ranks, Delete or Backspace removes, Tab crosses to the listbox and Shift+Tab comes back. Each chip's × is a button named `Remove {label}` and deliberately out of the Tab order, since Delete already does it and a stop per chip would double what a keyboard pays to cross the row. Every decision here — which chip ranks next, the editorial order, what the last chip may do, where the keyboard lands after a removal — is `utils/modelSelection.ts`, because Vitest has no DOM and anything left in the component is untestable by construction. The selection itself lives in `App.tsx` and the link, never here
- `src/utils/listbox.ts` — the two things that popover has to get right and a `<select>` got right for free: where the panel lands (`popoverBox`) and where the arrow keys go (`nextActiveIndex` down the list, `nextToolbarIndex` along the chip row above it — two functions rather than one axis flag, because both are on screen at once and one arrow key may move exactly one of them). Pure, because Vitest has no DOM and anything left in the component is untestable by construction. `popoverBox` clips the trigger's rect into the viewport before measuring from it — the panel is a scrolling column, so a short window puts the trigger below the fold and a raw rect invents room that is not there — and when the content fits neither side it overlaps the trigger to use the whole viewport, so a scrollbar means the screen is too short rather than the gap being too small. It returns the finished `offset` (`{top}` or `{bottom}`) rather than letting the caller re-derive it, which is a bug it already shipped once. It has exactly ONE caller, the hook below, and `styles.test.ts` fails a second
- `src/hooks/usePopover.ts` + `src/components/Popover.tsx` — the impure half of that, and the one recipe every floating panel follows (#385). Four components carried a copy of it and three had been built by copying the fourth, so a fix to one reached none of the others. **The hook is the wiring**: the two placement passes, both before paint (ask for the whole viewport so the panel lays out at its natural height, measure that height, place again knowing it — without the measurement the placement cannot tell "taller than the gap" from "taller than the screen", and every panel scrolls in the gap); the measuring ref, which runs after EVERY commit rather than keyed on `open`, because the panel does not exist yet when an `[open]`-keyed pass would run and the unmeasured fallback then sticks for the whole open; following the trigger on `resize` and on capture-phase `scroll`, since the panel is fixed and the trigger sits in a scrolling column; and the dismissal — Escape, which hands focus back to the trigger, and an outside **`pointerdown`, never `click`**, because a click landing on something that unmounts under it never reaches document and a press that starts outside has to dismiss before the map treats it as a gesture. The trigger is exempt, or its own toggle fires close-then-reopen. **The shell is the drawing**: the `SURFACE_CARD` wrapper, `LAYER.popover`, the fixed box, the portal to `document.body`, and an optional overline header row that two of the four had spelled separately. `remeasure` is what a panel whose height changes while it is open declares, and it is **empty by default**: a panel that re-places itself as its rows change can jump across its trigger under the hand pressing a row, which is worse than one that shrinks where it stands. `ModelPicker` is the one exception, because its chip row GAINS a line as models are ticked and would otherwise scroll in a gap the viewport could have given it outright. `preferredWidth` defaults to the 256px a list of labels takes; `ModelPicker` passes its own measured 380px because its rows carry prose
- `src/utils/modelSelection.ts` — which forecast models the picker has selected and which one of them RANKS, as pure rules (#232). Three invariants every caller leans on: the selected set is never empty, the ranking model is always in it, and `compared` never holds the ranking model, which is what lets the chart treat `compared` as the EXTRA lines beside the report's own. Order is editorial throughout — `/api/capabilities` publishes the models in `MODEL_INFO`'s declaration order, a ranking for mountain terrain rather than a sort — so the chips read in that order however they were selected and a `compare=` link means the same set of patterns whoever built it; an id this deployment does not publish keeps its place at the end rather than being dropped, since a link naming an unknown model is still that reader's link. `toggleSelected` is one row's tick AND a chip's ×, and its one interesting case is unticking the ranking model: the ranking passes to the next chip to the RIGHT, wrapping to the first, because the chips read in editorial order and the right-hand neighbour is the next model the list itself would have offered. `rankWith` is a chip-label tap and deliberately KEEPS the model it replaces selected — the old ranking model is a chip the reader is looking at, and taking it off the chart as a side effect of moving the highlight would remove something they never pointed at. `canRemove` is the last-model rule and `chipFocusAfterRemoval` is where the keyboard lands. It lives here rather than in the component for the reason `listbox.ts` does
- `src/utils/modelCompare.ts` — several models' answers over the charted destinations (#232), the pure half: the clamp (`compareEndMs`), the blend predicate, the colours, the live/commit predicate (`compareAdded`), the re-index of a fetched series onto the chart's grid (`modelSeriesOnGrid`), and `compareSeries`, which is **one line per (destination, model) pair** — three destinations under three models is nine lines. There is **no cap**: the #232 review removed `MAX_COMPARE_MODELS` because the ceiling hid the control that set it, and the spend is bounded by the Analyze click that buys it. **Every line is solid and COLOUR is the only channel.** A line style for the model is not an option here: `styles.ts` carries no stroke pattern table, and a chart whose point-sample window draws dots could not wear one anyway. **Every (destination, model) pair wears its OWN colour**, because a colour is what identifies a LINE and a model draws one line per destination: colouring by model put two lines of one model on screen in one hue, which is the ambiguity the encoding exists to remove. The pair (destination, RANKING model) keeps the DESTINATION's colour, the hue the marker and the table's checkbox already give it, so a chart with nothing compared draws exactly as it always did. Every other pair takes the next colour from `allocateColors` in `chartColors.ts` the first time it appears and keeps it for the session, however the list changes afterwards. That is the app's ONE allocator and the same one `useChartSelection` hands destinations their colours from: one counter over one palette is what stops a compared line and the destination standing beside it from being handed the same hue. `App.tsx` computes the pair map during render (allocation is deterministic, so the memo and the effect that persists it agree and no line flashes) and passes it into `useModelCompare`. Nothing else on the chart may pick a hue. The name carries both anyway (`comparedLineLabel` in `chartData.ts`, `1. Mount Rainier (NOAA GFS)`, rank then destination then model on EVERY entry, the ranking model's own lines included — a key that named the destination on one line and the model on the next was the review's second finding). The rank is `results`' ranking position, not `tableRows`', which follows a detail sort. A point-sample window draws dots rather than lines, and a dot carries the same colour, so the encoding survives it. `isBlend` reads the `blend` flag `/api/capabilities` publishes per model and never the `_seamless` suffix, which is Open-Meteo's naming habit rather than a contract: a blended product under another name would be drawn as one model with nothing saying otherwise, and a model the server did not publish is not a blend. `useModelCompare` resolves the `analyzed` window through `normalizeWindow` ONCE and uses the result for both the reach test and the fetch, because the snapshot records the request's RAW timestamps: a Current analysis is `start === end`, which unresolved fails every model's reach test and would ask Open-Meteo for a moment between itself and itself. A one-hour comparison draws one point per line. `hooks/useModelCompare.ts` is the spend, and it buys **one single-model `fetchWeather` per model over every charted destination at once, rather than one request naming several models**: a multi-model response collapses to BARE keys the moment any model named in it is out of domain (measured 2026-09-12 at 46.5,8.0, `models=gfs_hrrr,ecmwf_ifs025` answers HTTP 200 with `precipitation` and no suffix, which is one model's numbers under no label), so one model's absence would take its companion's lines with it. The split buys the per-model verdict — a single-model request 400s and names itself — plus the per-location+model cache and the vector-pinned aggregation itself, so a compared line and a re-analysis under that model cannot disagree. **A tick is a data knob and an untick is not.** The fetch is bounded by `analyzed.compareModels`, the set ticked when the analysis committed, so ticking a box afterwards draws nothing and cues `commitNeeded`'s existing `model-changed` reason (`compareAdded` is the predicate, and the asymmetry is the one every live knob has: unticking re-presents numbers already in hand and applies at once). A restored `compare=` link therefore buys its forecasts on the first Analyze and never on load. The clamp stops every line at the shortest reach on the chart, the ranking model's included, since a report's own line running past the models beside it is the ragged comparison the clamp exists to prevent; only the far end moves, because `forecast_hours` counts hours ahead of now and history is not model-limited. A comparison is a drill-down, not a knob: it never touches `present.ts`, the ranking, the markers or the CSV, and it is absent on air quality, which is one model (CAMS) whatever model ranks the field. The chart plots `ChartLine`s rather than rows (`chartData.ts`) for the same reason, and while a comparison is up it receives NO rows at all — the hook composes the ranking model's lines through the same product, so every entry is named and coloured in one place. `components/ModelCompare.tsx` carries NO key: a row of chips naming each model in its colour was built and removed (TJ, #232 review, round four), because the hover box already names rank, destination and model on every entry and the chips listed the models the picker already lists. What it renders is a note when a compared model drew nothing, and there is no `<select`, no `<button` and nothing that spends — pinned by a `?raw` test in `accessibility.test.ts`, because every control that shapes a comparison belongs in the panel's picker. **Which of those models are DRAWN is the results bar's `Models` link** (`components/ModelsPicker.tsx`, built from `ColumnsPicker`'s parts — same `popoverBox`, same outside-`pointerdown`/Escape dismissal, same `CHOICE_ROW`/`CHOICE_INPUT` rows — because it answers the same kind of question about the same kind of set). It stands under EXACTLY the condition `Columns` does — a bar that gains and loses members is a bar a reader has to look for (#242 review), and one row is a fine answer when one model is selected. Its rows come from the sidebar picker's SELECTION rather than from the chart (`modelRows` in `utils/modelVisibility.ts`: ranking model first, then the compared models in the picker's order), so a model ticked before the next Analyze already has a row. **Its rows carry NO colour**, checkbox and label only: a model has no one colour to show, because its lines wear one colour per destination, and a swatch there could only name one of them. The chart's hover box is where a line is identified, by its `1. Mount Rainier (ECMWF IFS)` name and its colour dot. It is PRESENTATION ONLY: the forecasts are bought either way, so hiding must not cancel a fetch and showing must not start one, which is why `hidden` reaches `useModelCompare` as a filter on `shown` and never on `drawnIds`. There is no floor — every box may be unticked, because an empty chart is the honest answer to "hide everything" and a last-one-standing rule is one the reader finds by pressing something that does not respond. It rides in no URL parameter and no storage: a shared link is the comparison that was bought rather than one reader's view of it. `utils/modelVisibility.ts` owns the rules (`visibilityRows`, `shownModels`, `toggleHidden`, and `pruneHidden`, which drops the flag of a model that leaves the picker's selection so one picked up again comes back drawn); a hidden model also bounds no clamp and explains no absence, since its lines are missing by instruction
- `src/components/MapView.tsx` — the map, and wiring only: the MapLibre instance, the sources and layers in the order the `load` handler adds them, the popups, the drag handlers, and the overlay effects. The explicit-timestamp form (`ridge::USCOMP-N0Q-YYYYMMDDHHMM`) returns 200 for timestamps this mosaic never produced and `USCOMP` is not a documented RIDGE id — undefined behavior, do not build on it. Because the offsets are relative, the readout is a relative time and a pan mid-loop can pull newer imagery into an older frame; both are documented rather than engineered around
- `src/utils/smoke.ts` — `GET /api/smoke` client + popup formatting, mirroring `wildfires.ts`. Owns the three-density paint table that both the map layers and the legend read, so the picture and its key cannot disagree. Stone rather than slate, because slate is the app's own surface family and a slate plume reads as chrome that escaped onto the map; opacity is the whole encoding, so overlapping plumes darken in the direction they should
- `src/utils/legendRamp.ts` — how a banded scale is DRAWN in the map's legend (#454), for every scale on the map: `rampCss` turns a band table into the strip's CSS and `rampTicks` places the numbers under it. Whether a strip blends follows the DATA rather than taste — a metric marker is interpolated between anchors so its strip blends, NOAA's snow bands are a classification so its strip is hard-stopped — and every strip is equal-width per band, never to scale, because 0.39 to 787 inches to scale is ten bands in two pixels. A tick hangs from the nearest edge that keeps it in the box: the last from the strip's end, one on the strip's left edge from the start, everything between centred on its boundary. `scaleTicks` prints THREE of a metric scale's five boundaries, which is measured rather than chosen: five land 27px apart on a 162px strip and the freezing level's are 28 to 33px wide, so they overlapped into one run of digits (Chrome, 2026-09-17). The numbers are the thresholds themselves formatted, never captions written beside them, so a tick cannot disagree with the colour it names, and they carry NO unit: the section's label does (`metricLabel` in `metrics.ts`, reading the SCALE's unit, so playback's swap to `in/hr` relabels the strip with its bands), which is what keeps `AQI` a bare noun and the strip's widest label three characters shorter (TJ, 2026-09-17). The snow layer is the exception, its label's parentheses already holding the credit its licence asks for, so its unit stays on the last tick
- `src/utils/snowDepth.ts` — the NOHRSC snow depth overlay's pure half (#446): the tile-URL builder, the source and layer ids, the coverage extent, NOAA's twelve-band legend table and the strip the legend draws from it (through `legendRamp.ts`, the same builder the metric key uses). The service has no cached tiles (`singleFusedMapCache` is false and it advertises no Tilemap), so the layer is an ArcGIS `export` call driven as a raster source through MapLibre's `{bbox-epsg-3857}` token, and `imageSR=3857` is not optional — the service's own reference is EPSG:4269 and an image in it does not sit on a Web Mercator map. Three things bound what the layer costs, because the service refuses caching outright (`max-age=0, must-revalidate`) and renders every image on request: a 512 px tile, since a render costs ~0.46 s whatever its size; the extent as the source's `bounds`, so nothing is asked for outside the analysis; and `SNOW_MAX_ZOOM`, past which the 1 km grid has no more detail and MapLibre magnifies what it holds. The colours are NOAA's, decoded from the legend endpoint's swatches, for the reason the radar legend takes IEM's: the map draws NOAA's rendered image, so the key has to describe that image. The first band is transparent by NOAA's own paint, which is why the ramp has eleven blocks and not twelve. Measured 2026-09-16: 11 renders fill a 1440x597 map, 4 to 6 more per full-width pan, 200 to 255 ms each; a 402x874 phone pays 6 and 0 to 3
- `src/utils/wildfires.ts` — `GET /api/wildfires` client + popup formatting for the wildfire overlay (US-only, best-effort). It does **not** call NIFC: since #203 both fire fetches go through the pod's snapshot, because NIFC's quota is its ArcGIS org's and shared with every consumer of the public dataset, so per-visitor requests crowded one invisible pool and lost at random. The caller names the fidelity it needs — the app asks for `coarse` for drawing and measuring alike (56 m of simplification cannot move a 10-mile answer shown at 0.1 mi); `full` stays on the API for callers who need surveyed shapes; `COARSE_TOLERANCE_DEG` mirrors `COARSE_OFFSET_DEG` in `nifc.py`. The popup's one dated line is `attr_ModifiedOnDateTime_dt`, when NIFC last revised *that perimeter* (measured range across one national snapshot: minutes to two weeks). It reads "Last updated:" because it is the *only* date shown. The response's `fetched_at` is deliberately **not** surfaced in the UI: the cache serves an aged snapshot rather than failing, so a visitor's answer never hinges on a fetch of their own, and a freshness line on every fire would be noise about an internal detail. It stays in the payload for API callers, who have no other way to know how current an answer is
- `src/utils/fireProximity.ts` — pure point-to-perimeter distance math flagging results within 10 mi of an active fire (`FIRE_WARN_MILES`; 25 was tried in the #275 review and rejected as too wide), plus `pointsKey` (the order-independent identity of a destination *set*); driven by `src/hooks/useFireProximity.ts`, which queries once per analysis around the whole candidate field, not the displayed rows — those are re-derived on every live knob change, and keying off them would mean a NIFC query per twiddle (independent of the overlay toggle). The lookup asks for the **coarse** copy: ~56 m of simplification is 0.035 mi against the 10-mile threshold shown at 0.1 mi, and a thirteenth of the bytes. The hook keys its effect on `pointsKey`, not the array reference, or a re-rank aborts the request in flight and refetches the same question. It returns a **status** (`idle`/`loading`/`ready`/`unavailable`) and an **`uncovered` key set** beside the warnings, retries a failed lookup, and logs the caught error: every failure mode used to collapse into one empty map, so the feature's failure was indistinguishable from its all-clear. `ready` + empty means checked and nothing near; `unavailable` means the caller must not imply either; `uncovered` (#256) is the geographic case of the same rule, per row — WFIGS is US-only, the server publishes its coverage outline as a foreign member on `/api/wildfires` (coarse, outward-biased, Alaska split at the antimeridian; `wfigs_coverage.py`), and a destination outside it was never checked, so its cell in the **Wildfire (mi)** column — the table's and the CSV's alike (`WILDFIRE_COL` in `tableColumns.ts`; its key is virtual, so it sorts and renders out of the warning map rather than the row) — reads `N/A`, distinct from the mark a cleared check leaves (a dash on screen, a blank cell in the file), so a missing warning is never mistaken for a clear one. - `src/utils/polygonEdit.ts` — where a click belongs in the ring being drawn (#118). Every new point used to go on the end of the array, which is fine while you are tracing an outline for the first time and wrong the moment the ring is closed: a click on the far side joined it to whichever vertex happened to be last, and the ring crossed itself. - `src/utils/polylabel.ts` — the interior point furthest from any edge (the pole of inaccessibility), which is the coordinate a clicked lake becomes a destination at (#119). Mapbox's quadtree search, pruned by each cell's best possible score, so a lake costs a few hundred distance evaluations rather than a scan of its area. `widestPole` runs it per polygon and keeps the roomiest, because a lake arrives as however many pieces of it are currently drawn and concatenating their rings would have the even-odd test read one piece's outline as another's hole
