# Frontend layout

Every module under `frontend/src/`: what it owns, and why it is separate. This
file is one half of the module layout that used to sit in the repo root's
[`CLAUDE.md`](../../CLAUDE.md), and it is loaded only when a session touches this
tree. Everything that governs a change to these modules — the design-system rule,
the memoization rule, the Python/TypeScript mirrors table, the interaction model —
stays in that root file. Read it first; this is a directory, not a manual.

**A new source module gets a bullet here, in the same PR that adds it.** The bullet says what the module OWNS and why it is separate, at the density of the ones around it; one line is a fine answer for a twenty-line module. Nothing enforces this. A session reads this list before it writes code, so a module named nowhere here is one the next session rediscovers and re-decides (#392).

- `src/components/ForecastCalendar.tsx` — the whole forecast window in one card: a **When** segment picking Current or Dates, an **Hours** segment under it, and the month grid below both. The two segments sit above the grid rather than around it, so the two decisions the window needs read as one block and neither lands below the fold; the grid and the Hours row appear only under Dates, the way the hour fields appear only under Hourly, because Current takes no input at all. "Dates" names the second arm rather than Days or Range because it must be silent about count *and* tense: 55 of the 71 days it reaches are behind today (#234). Holds no date logic of its own (see `utils/calendar.ts`); a mouse drags a range, a finger taps twice, and the selection commits on pointerup so a drag never re-renders the panel per pointermove. Cell brightness is one channel carrying one meaning — **how much of that day the app can serve** (`DayAvailability`) — which is why an adjacent month's days are drawn blank rather than dimmed
- `src/components/SearchBox.tsx` — floating map search (Nominatim place lookup + local coordinate parsing; Enter-to-search only, per Nominatim's no-autocomplete policy)
- `src/components/ResultsTable.tsx` — sortable results table, and *only* the rendering of one: it receives its rows already in display order. It is the frame: the header, the empty reason, and one memoized row per destination, keyed by `rowKeys` (the coordinate and the compared model) so a sort moves rows rather than re-keying every one. The chart handlers come from `useChartBox` and the fire clock from `FireClock`, so neither a chart toggle nor a clock tick redraws every row; the linter's `table-row-memo-props` check fails an inline function or a fresh empty literal on a row, for the reason `app-memo-props` fails one on the table, and `ResultsTable.test.tsx` counts the rows each render draws, because the stabilities built outside the JSX (the hoisted empty widths, the memoized coloured group, columns and keys) are ones the lint cannot see.
- `src/components/ResultsTableRow.tsx` — one body row, ranked (the default export) or pending (`PendingRow`), each memoized (`app-memoized` holds the default export, `table-pending-row-memoized` the named one): the rank cell with its remove ×, the chart checkbox, and every cell's markup and links, each cell a component. It also owns `FireClock`, the wildfire cells' shared 400 ms clock, which reaches the cells through a context rather than a row prop so a tick redraws the wildfire cells and no row. Apart from the table because a report can hold a thousand rows and most changes touch few of them. Every prop is a primitive, a value the table memoizes, or a stable callback. `sized` from the header wraps every cell, so the body and the header read one set of widths
- `src/components/ResultsTableHeader.tsx` — the results table's header row and every gesture on it, apart from the body because none of it reads a row, and memoized on its own so the body's re-renders do not redraw it; `ResultsTable` memoizes the columns and the chartable rows it hands over for the same reason. Every header CLICK sorts the rows on screen in place and nothing more — the panel's Ranking control is the only thing that re-ranks the field, reorders the column groups, or moves the shading (#242 review). The display order is `App.tsx` state (`detailSort`) so the CSV export can leave in it. A header DRAG is the one other thing a header does, and it moves the column rather than the rows (see `columnDrag.ts`); the two are told apart by distance and by hold, never by which of them fired first, because a tap must still sort. Both the drag listeners and the resize listeners live on `document` rather than on the `th`: a drag leaves the cell it started in on its first frame. It also owns `sized`, the wrapper every cell renders in, because auto-fit measures that wrapper, and the drag ghost and insert line, portalled to the body
- `src/hooks/useAnalyze.ts` — one Analyze click, composed: the run in flight (`useAnalysisRun`), the report it commits (`useAnalysisReport`), and the work between them (`utils/analysisPipeline.ts`). What stays here is what spans runs: the forecasts the next run may reuse, set only once a run has committed, and the request `retry` repeats. The returned object is the API `App.tsx` destructures, and `useAnalyze.test.tsx` pins its names and their order. The one path since #240: an unreachable Open-Meteo fails the analysis with its own message rather than rerouting through the server's shared quota. Its public types (`Progress`, `Refusal`, `AnalyzedView`, `AnalyzeOptions`) live in `analyzeTypes.ts` and are re-exported here
- `src/hooks/useAnalysisRun.ts` — the analysis in flight: `loading`, the status line, progress, the pace countdown, cancel, and the error or refusal a failed run shows. Apart from the report because the two reset on different events: this clears when a run starts (which is what re-arms a dismissed notice), the report only when a new one commits. Which box a failure lands in is `utils/analysisFailure.ts`
- `src/hooks/useAnalysisReport.ts` — the committed report: `response`, the full field (`universe`), the `analyzed` snapshot, `arriving`, `analysisSeq`, and the candidate field published for the wildfire check with its own `fireSeq`. Apart from the run because it outlives one: a cancel or a failure leaves it standing. `analysisSeq` moves on a full commit only, never on a partial one
- `src/hooks/analyzeTypes.ts` — the shapes `useAnalyze` hands its callers: a run's progress, a refusal, the `AnalyzedView` snapshot a report was analyzed under (it composes `present.ts`' `AnalyzedSnapshot` rather than restating it), and the options a run records. Types only, apart from the hook so a component or a pure module can name them without reading the hook; `analyzeTypes.test.ts` holds them to the hook's re-exports at the type level
- `src/utils/apiFetch.ts` — the one door to Bluebird Forecast's own API (#381). `fetch` rejects with a `TypeError` before any status exists when the pod cannot be reached, and the browser writes that sentence itself, so six call sites each carrying their own fetch stack meant the error banner could read "Failed to fetch" — a raw exception message, which `docs/STYLES.md` forbids. The translation therefore lives at the primitive rather than at each caller, and the linter's `one-api-door` check pins that **no file under `src/` reaches for `fetch` except this one and `openMeteo.ts`**, so the next caller cannot reopen it. What it does not own is the meaning of a status: `apiFetch` returns the `Response` whatever the status came back, because a 429 is a rate-limit flag on the overlays, a refusal body on analyze, and a silent fallback on capabilities. `apiJson` layers the `ok` check and the parse on top for the callers with nothing to say about either, and `postDestinations` is shared because two modules make that one call and neither can own it. An abort passes through untranslated, a cancel being the user's own doing. Open-Meteo deliberately keeps its own stack: its taxonomy is a quota, a model domain and a pacer, none of which is about our own pod being up
- `src/utils/openMeteo.ts` — the browser's Open-Meteo HTTP client: the weighted pacer, the endpoint split (`fetchSpans`), the requests, and `windDirectionSeries`, which is browser-only and so stays out of the pinned port
- `src/utils/openMeteoAggregate.ts` — the line-for-line port of `backend/app/services/aggregation.py` and nothing else (#405), pinned to it by `weather_vectors.json` (round-half-even, naive-UTC stamp parsing, zip-vs-series loop asymmetry all deliberate). Its own module so the two halves of the contract read side by side: `openMeteoAggregate.test.ts` reads both files and fails when their functions differ in name or order
- `src/utils/openMeteoErrors.ts` — the Open-Meteo failures the browser tells apart and the sentences they carry (`COVERAGE_PHRASE`, `COVERAGE_MESSAGE_TAIL`, `BAD_BODY_MESSAGE`), the mirror of `backend/app/services/errors.py`. Its own module because both the client and the port throw them, and the client imports the port, so either home would be an import cycle
- `src/utils/clientAnalyze.ts` — ports of the analyze route's align/assemble/rank helpers (the forecast bounds are `constraints.ts`, re-exported here) + the browser-side candidate cap, plus `resolveCustomOnly` (the custom-only path's one server call, a nicety that degrades to unresolved rows on any failure; it asks about EVERY list now, where a list whose rows already knew their elevations used to skip the round trip, because today's snow depth is a second thing only the pod can answer and skipping would leave a pinned summit reading `N/A` beside the same summit inside a drawn ring reading a number — #449). No `_merge_custom` port: the server merges on the way in, and a second union here could only disagree with it; returns the trimmed `response` **and** the full ranked `universe`, and owns `refreshEchoRows` (which field a re-analysis re-ranks, and how removals apply to it) beside the two predicates that decide whether an Analyze re-discovers at all (#382): `discoveryBase` spells the user-authored discovery inputs as one string (ring, sorted kinds, unnamed-peaks toggle, parsed CSV rows, and nothing a live knob touches), and `isDiscoveryRefresh` reads a `DiscoveryRecord` against it. That decision is a spend boundary, so both directions are pinned by tests: a matching base whose searched list only SHRANK refreshes weather alone, where a NEW searched place (which must compete against the whole candidate field the echo is not) or any base change buys a fresh Overpass query. The polygon guard stays in `App.tsx`, because a run with no ring is not a polygon discovery whatever the record says
- `src/utils/analysisPipeline.ts` — one browser analysis from request to report, around `clientAnalyze.ts`: that module fetches, aggregates and ranks a field it is handed, and this one finds the field (`discoverCandidates`: discovery for a ring, resolution for a custom list, and `readErrorBody` for a refused answer), asks `forecastReuse.ts` whether a held field may stand in, shapes each partial field for the screen, and merges the truncation discovery reported with the one the ranking applied (`runAnalysisPipeline`). No React, so its order of events is testable in the node project
- `src/utils/forecastReuse.ts` — whether a held field may stand in for a fresh fetch (`reusableForecasts`: the same resolved window and model, strictly under `FORECAST_REUSE_MS`), and what to hold after a run (`holdForecasts`, which keeps the FIRST fetch's clock so re-analyzing every fourteen minutes cannot keep a field alive). `FORECAST_REUSE_MS` mirrors the pod's per-location TTL (mirror row 21 in the root `CLAUDE.md`)
- `src/utils/analysisSnapshot.ts` — the `AnalyzedView` a report records (`analyzedView`) and whether a request fetches the cloud column (`requestsCloud`). Built off the request plus the facts it cannot say (the discovery identity, the compared models, the snow date its own discovery returned), with the window classified once, at commit
- `src/utils/analysisFailure.ts` — which box a failed analysis lands in and the sentence it says: a cancel shows nothing, a refusal goes to the warn box, and the model-coverage sentence is composed here from the picker's label and `COVERAGE_MESSAGE_TAIL`
- `src/utils/constraints.ts` — the forecast bounds as one value: `Constraints` and `NO_CONSTRAINTS`, the `LOWER_BOUNDS`/`UPPER_BOUNDS` table of which result field each bound compares (the port of `_LOWER_BOUNDS`/`_UPPER_BOUNDS`, mirror row 17), the wire conversions both ways, and `filterConstraints`, which `present.ts` runs over the held field. Apart from `clientAnalyze.ts` because none of it fetches: every bound re-reads rows already in hand, which is what makes it a live knob. `clientAnalyze.ts` re-exports it, so every importer kept its path. It also holds `namesOnRequestMetric` (mirror row 29), the one question a bound can raise about a fetch: whether the ranking or a bound names the cloud column, which an analysis fetches only on request (#117)
- `src/utils/forecastStore.ts` — the per-location forecast cache, in memory for 15 minutes and across a reload (#337). The in-memory `Map` and its reload snapshot live together, so one module owns both halves of the one cache. A budget rather than a mirror: one entry measures ~10.5 KB and `sessionStorage` holds ~5 MB, so a maximal 1,500-destination analysis (15.7 MB) cannot fit and the newest entries are kept up to `MAX_BYTES`. The stored expiry is wall-clock (`Date.now()` at the write plus the ms remaining), because the in-memory one is a `performance.now()` reading that restarts at zero on reload. Every storage call swallows its failure: a private window, cleared site data, and a full quota all look like an exception from an ordinary property access, and none is a reason to fail an analysis. Measured working: a reload re-ran a 946-destination analysis with **zero** Open-Meteo calls from a 646 KB snapshot
- `src/utils/present.ts` — the one derivation from held field + live knobs to displayed rows (`presentResults`, reporting `eligible` and `excluded` so a bound that empties the table is nameable), plus `commitNeeded` (every knob that has stopped applying live, and why: a forecast window that is no longer the one behind the rows, a forecast model that is not the one every held number came from, a changed search ring or type set, a destination the analysis never covered — all that apply, in the fixed order model, window, polygon, types, destination)
- `src/utils/tableColumns.ts` — the column set itself (`COLUMNS`, with an optional `csv` projection where a display formatter would be unparseable) and the one derivation of which columns a report shows (`displayedColumns` = point-sample collapse, then ranked group lifted to the front, then `withModelColumn` inserting **Model** directly after **Name**, the column it qualifies). The table and the CSV export both read it, so a file's columns cannot disagree with the screen's. `applyColumnOrder`/`moveColumn`/`stepColumn` lay the reader's own order over that derivation: it is stored under `bluebird_forecast_view.columnOrder`, it is deliberately NOT in the URL (a shared link opens in the standard order), the CSV follows the screen, and **a change to `Rank by` discards it** — ranking lifts its own metric group to the front and TJ chose to let ranking win (2026-09-14). The discard is guarded by a `rankedOnce` ref in `App.tsx`, because the effect that watches `sortBy` also fires on mount and was wiping a stored order on every page load. **Model** is the one column whose default depends on the report (off with one model, on with several, `bluebird_forecast_view.modelColumn` holding a reader's tick once they make one), which is why it is always offered in the Columns picker rather than appearing and vanishing. **Snow depth** is the one column that is not a reading of the window (#449): it is listed in `POINT_LABELS` under the same label it carries in window mode, because that map is also what decides which columns a point sample KEEPS and a metric absent from it disappears from the narrow table
- `src/utils/viewPrefs.ts` — everything one browser remembers about how it reads a report, under `bluebird_forecast_view` and `bluebird_forecast_welcomed` (#382): the results mode an explicit press chose, the column set, the Model column's own answer, the reader's column order, and the welcome flag. Read and write, the way `urlState.ts` splits the URL, and kept apart from it for the reason that split exists: a link is the session someone shares, and these are one browser's habits that no link should carry. One parse per mount rather than the six inline reads `App.tsx` used to carry, each behind its own try/catch and only one of them running the column migration — `columns` predates the wildfire column (#288), `columns2` predates the freezing level (#295) and `columns3` predates snow depth (#449), so each generation migrates with the newer keys added rather than being read verbatim, and the write that supersedes a generation deletes it. Every accessor is total: a storage that refuses (private window, full quota, no `window` at all) yields the defaults, which is the guard the welcome flag was missing. the linter's `app-no-storage` check fails any `localStorage` in `App.tsx`, so a seventh inline read cannot reappear
- `src/utils/columnDrag.ts` — the pure half of dragging a column, shared by the table header and the Columns picker so one gesture means one thing in both (`DRAG_THRESHOLD_PX`, `LONG_PRESS_MS`, `dragBegins`, `keyAtPosition`, `dropEdge`, `ghostLeft`). Here rather than in either component for the usual reason, and `ghostLeft` specifically because the ghost ran off the right edge of a phone before it was measured rather than positioned
- `src/utils/windy.ts` — where a metric cell or a popup row links to on Windy (`windyModel`, `windyTime`, `extremeHourMs`, `windyUrl`). Windy's deep-link grammar is undocumented and was measured against the live site on 2026-09-14; the file's head comment is the record of it, including that the time token is **UTC**, that Windy snaps the hour to the model's own step, and that it ignores an hour in the past. Model tokens were read from Windy's own `W.products` registry and matched by PROVIDER, so a reader who picked the Met Office lands on the Met Office's model; a regional token outside its domain falls back to ECMWF on Windy's side, which is what lets this file carry no coverage polygons. Snow depth is absent from `EXTREME` rather than mapped to a series, because it names no hour at all: the link opens `snowcover` at Windy's own "now" (#449)
- `src/utils/resultsCsv.ts` — the displayed report as a file (`buildResultsCsv`, `csvFilename`). Pure and DOM-free so it is testable under the node-env Vitest; the Blob and anchor live in `App.tsx`. Takes rows already in display order and columns already resolved — it re-derives nothing, because a second answer to "what is on screen" is the bug `present.ts` exists to prevent. A `null` fire map **drops the wildfire column** instead of writing it blank: on screen an empty flag column self-corrects when the ⚠️ arrives a moment later, but a file is read detached from the app, where a column of blanks asserts that every row was checked and cleared. Below the data, a metadata block states the analyzed window as `Forecast start` and `Forecast end` rows, plus one `Forecast end (<model>)` row per compared model that ends inside the window (#493, `CsvOptions.modelEnds`, in the picker's order), so a spreadsheet can compute the hours a short model's plain numbers cover
- `src/utils/resultsCells.ts` — what a results-table cell SAYS: the wildfire text and its hover note, the Model column's fallback, the N/A of a metric that declined to answer, the printed value (snow ceiling mark included), a ranked cell's colour, the Windy link, the rank, and the row keys. Apart from `ResultsTableRow.tsx`, which is the markup, so each decision is testable under the node-env Vitest without rendering a table
- `src/utils/forecastWindow.ts` — window normalization twin of `models/analyze.py` (point sample → floored hour + 1 min; horizon checks), plus `windowSource` (which Open-Meteo endpoint answers a window, or that it spans the archive boundary and both do) and `archiveBoundaryMs` (the one instant that seam falls on, mirrored with `limits.py` — #123) and `hourlyStampCount`/`isPointSample`: how many hourly stamps the inclusive filter matched, which is what decides the collapsed table columns instead of a mode name
- `src/utils/calendar.ts` — the forecast window as a calendar (#166), as a barrel over the five flat sibling modules below, so every importer kept its path. Flat rather than a folder, because the linter's `style-one-placement` check globs `src/utils/*.ts` and a folder would escape it. Together they own the servable band, the `ForecastSelection` type (`now` | `days` with optional narrowed `hours`, plus the dateless Dates arm — today outlined, nothing selected, Analyze blocked — that a fresh switch to Dates opens on), month-grid generation, the click/drag reducers, and the conversion to the `datetime-local` pair everything downstream reads. All of it pure, so the node project checks every case without a page and `ForecastCalendar.test.tsx` has only the wiring left to show: the component is wiring only. **The band's far edge is the nearer of two limits, and only one of them is per model.** The hard one is the API's: `FUTURE_LIMIT_DAYS` is 15 (Open-Meteo's "16 days" counts today) and `bandEnd` walks back a further day wherever a local 23:59 lands on the next UTC date, because the request carries UTC dates. The soft one is the selected model's, carried in **hours** rather than days and passed in from `/api/capabilities`. Hours because a model's reach is set by when its last run started, so it lands mid-afternoon as readily as at midnight — rounded down to whole covered days, HRRR's 42 h would offer *today only* anywhere west of Greenwich, which for a short-range mountain model is the same as not offering it. A day the reach lands partway into draws `partial`, the state `DayAvailability` already uses for "we can serve some of this day". `clampSelection` is what a model change does to a window that no longer fits: both ends clamp independently, and it returns `null` for "unchanged" so the panel warns only when something actually moved. `classifyWindow`/`classifyAqiCoverage` read the same band so the grid and the warnings cannot disagree; they sit beside it in `calendarBand.ts`, and `urlState.ts` re-exports them. Both edges now ride in one `BandLimits` object rather than as two number parameters, because 384 hours and 365 days are adjacent arguments of the same type and a transposed pair would compile. The NEAR edge is no longer compiled here at all: it is the archive's reach from `/api/capabilities` (#123), and the days it opens up draw as `full` because the archive holds every hour of them and air quality reaches over them too. It also owns how a window says its own dates: `windowPhrase`/`windowCaption` behind the results header, `snapshotCaption` where a snapshot metric ranks and there is no window to name (`Snow depth as of Sep 22`, #449 — parsed as a LOCAL day, because `Date.parse` reads a bare `YYYY-MM-DD` as UTC midnight and would print the day before west of Greenwich), `archiveSeamPhrase` behind the panel's seam line, and `needsYear` — the one predicate deciding whether a date carries its year (the window's years against the reader's, either end, so both ends carry it or neither does), because a year-old report otherwise reads as four days of `Sat, Sep 13`. Every one of them takes an injectable `now`, so nothing here passes or fails on the year the suite runs in
- `src/hooks/useForecastSelection.ts` + `src/utils/forecastSelection.ts` — the panel's When and Model state, cut out of `App.tsx` (#409): the selection, the ranking model, the compared models, the clamp notice and the pre-clamp memory, plus the three things read off them every render (`panelWindowMs`, `panelPointSample`, `windowWarning`). One hook because a model change edits the window, so the two cannot be owned apart without handing each other setters. The rules are pure and live in the util: `planModelChange` is the clamp and its undo (a pre-clamp window comes back whole the moment a model can serve it, and a chain of clamps remembers the FIRST window), `panelWindowMs` the whole-day stand-in a dateless selection borrows, and `windowWarningFor` the horizon warning. `forgetPreClamp` is the one call an analysis makes, because a report pins the window it asked and a restore after it would disagree with the screen. The linter's `forecast-selection-hook` check keeps `panelPointSample` read off the PANEL window, where the report's `pointSample` stays in `App.tsx` (#485)
- `src/hooks/useRankingKnobs.ts` — the presentation knobs: the ranking, its direction, each metric row's aggregate, the forecast bounds and the results cap, plus `liveKnobs`, the one memoized value `present.ts` re-derives the table from. Its own hook because these knobs apply live and never reach the data side of a request (#188), and because `liveKnobs` must keep its identity across a render that changed no knob or the table re-derives for nothing. It owns the limit re-clamp once `/api/capabilities` lands (only ever lowers) and `clearFilters`, which clears the bounds and the cap together because they are one column of the Metrics table (#341)
- `src/utils/calendarDates.ts` — `YYYY-MM-DD` days and `HH:MM` times: parsing, validation (`isValidDatetimeLocal` included, which the URL codec and the classifiers share), and day and month arithmetic through the Date constructor's field overflow, because a local day is 23 or 25 hours on a DST transition. The rest of the calendar reads these rather than doing arithmetic of its own
- `src/utils/calendarBand.ts` — the servable band: `FUTURE_LIMIT_DAYS`, `BandLimits`, `bandStart`/`bandEnd`, `inBand`, the air-quality horizon, and the two classifiers `classifyWindow`/`classifyAqiCoverage` (re-exported by `urlState.ts`, whose suite still tests them). One module, so the grid's unpickable days and the warnings' out-of-range windows are computed by the same functions
- `src/utils/calendarGrid.ts` — the month grid: `monthGrid`'s cells marked `full`/`partial`/`unservable` against the band, `monthHasBandDay` for the month navigation, and the weekday and month labels
- `src/utils/calendarSelection.ts` — `ForecastSelection` and its reducers: a click with a pending anchor, a drag, a clamp to a band that moved under the selection, a switch of arm, and the `datetime-local` pair a selection asks about. Reducers rather than handlers in `ForecastCalendar.tsx`, so the node project pins what a click means
- `src/utils/calendarPhrases.ts` — how a window says its own dates: `windowPhrase`/`windowCaption`, `snapshotCaption`, `archiveSeamPhrase`, and `needsYear`, the one rule for when a date carries its year
- `src/components/ModelPicker.tsx` — the forecast model as a button opening a listbox of all of them, in the app's one popover shell and placed by the app's one popover hook (see the bullet below), so it is portalled to `document.body` and positioned fixed like every other panel. A native `<select>` cannot do this job: choosing well means reading eight summaries against each other, a select shows one at a time, and its options cannot carry them (the shortest needs 303px of label where the control has 245px). `title` on an option is no way out either — macOS draws the list as an OS menu that renders no tooltip, and a phone has no hover. Fixed rather than absolute because `ControlPanel` is an `overflow-y-auto` column that would clip a child at the scroll boundary. It takes a `disabled` prop for the one window the model does not apply to (an archive window, #123 — a window that CROSSES the boundary keeps the picker, because its forecast half is the chosen model's), wearing `DISABLED` rather than disappearing: a control that vanishes takes its label and its last value with it, and an info line under Analyze says why it is faded (it was a `title` on the trigger until 2026-09-14, out of reach of every touch reader). It is also where the chart's model comparison is chosen (#232), and the popover is **two parts with one gesture each**. **The LIST selects**: tick a row's box or click anywhere on the row, untick to remove, and nothing on a row ranks or closes the popover. **The CHIP ROW above it ranks**, under a `Selected models` header drawn in the list header's own recipe so the popover's two blocks read as two parts of one control: one chip per selected model in the published editorial order (never the order selected), the ranking model's chip highlighted with `CHIP.active`, and a tap on any other chip's label moves the highlight to it — the `model-changed` data knob, window clamp included, with the model it replaces keeping its chip. The split is the design: one row that both selected and ranked put two gestures a few pixels apart, one of which dismissed the list under the reader's hand. A chip's × deselects it; the ranking chip has none, so unticking its ROW is how it goes, and the ranking then passes to the next chip to the right, wrapping to the first. The last selected model cannot be given up — no ×, and its row's box disabled — because a report has to come from some model, and `role="option"` carries `aria-disabled` to say so. Nothing inside the popover closes it: Escape and an outside `pointerdown` only, which is `usePopover`'s rule rather than this file's, so the Columns picker closes the same way by construction. The closed trigger reads `{label} +{n}`, the label ellipsizing rather than widening past `CONTROL_W`, because the count is the only thing on it a reader cannot otherwise see. The listbox is `aria-multiselectable` and `aria-selected` means "on the chart"; the drawn checkboxes are `aria-hidden` with `tabIndex={-1}`, because a focusable input inside a `role="option"` would be a second tab stop in a list whose whole keyboard model is one element plus `aria-activedescendant`, and Enter and Space both toggle the active row. The chip row is a `role="toolbar"` with a roving tabindex: ArrowLeft/ArrowRight/Home/End walk it (`nextToolbarIndex`, the horizontal twin of `nextActiveIndex`, separate so one arrow key moves exactly one of the two parts), Enter ranks, Delete or Backspace removes, Tab crosses to the listbox and Shift+Tab comes back. Each chip's × is a button named `Remove {label}` and deliberately out of the Tab order, since Delete already does it and a stop per chip would double what a keyboard pays to cross the row. Every decision here — which chip ranks next, the editorial order, what the last chip may do, where the keyboard lands after a removal — is `utils/modelSelection.ts`, where the node project checks every case; `ModelPicker.test.tsx` shows that the gestures reach it. The list takes the keyboard when the panel is DRAWN rather than when `open` turns true, for the reason the hook's measuring pass runs after every commit: on the first open of a session the panel exists one render later, and an `open`-keyed focus left the keyboard on the trigger. The selection itself lives in `App.tsx` and the link, never here
- `src/utils/listbox.ts` — the two things that popover has to get right and a `<select>` got right for free: where the panel lands (`popoverBox`) and where the arrow keys go (`nextActiveIndex` down the list, `nextToolbarIndex` along the chip row above it — two functions rather than one axis flag, because both are on screen at once and one arrow key may move exactly one of them).
