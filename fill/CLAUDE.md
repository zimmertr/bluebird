# Planet fill layout

Every file under `fill/`: what it owns, and why it is separate. The planet fill
builds the shared cache's places table from the OpenStreetMap planet file
(#760), in an image of its own, because it needs osmium and a scratch volume the
app's pod has neither of. The rules that govern a change here, the mirrors table
among them, stay in the repo root's [`CLAUDE.md`](../CLAUDE.md), and the app
modules the fill works beside (`app/db/`, `app/services/osm/rules.py`,
`app/services/places/`) are in [`backend/CLAUDE.md`](../backend/CLAUDE.md). Read
those first; this is a directory, not a manual.

**A new file here gets a bullet, in the same PR that adds it**, at the density of the ones around it (#392).

- `fill/fill.py` — the whole job, run by the chart's daily CronJob as `python3 fill.py` with its settings in the environment (`DATABASE_URL`, `SCRATCH_DIR`, `PLANET_URL`, `REPLICATION_URL`, `FORCE_FILL`, `SCHEMA_WAIT_S`). It checks, and fills only when it must. The check waits up to `SCHEMA_WAIT_S` for the app's migrations to create `osm_state`, since the fill and a new database's first pod can start together, takes the `planet-fill` advisory lock for the whole run so a second fill leaves the work to it, and exits when the table was filled under this release's `rules.RULES_VERSION` (`is_current`), which is most days. A first run, a rules change or `FORCE_FILL` fills. `state.txt` is read first, so a replication server that is down fails the run before an hour of download. The planet downloads with Range resume over `DOWNLOAD_ATTEMPTS`, is checked against its published MD5, with the `.md5` read once more on a mismatch because the planet is republished weekly under one name, and must fit the scratch volume with `SCRATCH_MARGIN` to spare. Then `osmium tags-filter -R` keeps `CANDIDATE_FILTERS`, a superset of the rules because tags-filter can test neither a name against a pattern nor a key for absence; `keep_ids` asks `rules.classify` which to keep; `osmium getid -r` copies those out with everything they reference (its exit 1, a member missing from the file, is accepted with a warning); and `place_elements` puts each at the centre of its box by `rules.relation_boxes`, with node locations in an on-disk `sparse_file_array` index, because a Python dict of the planet's points would take tens of GB. `load_and_swap` copies the rows into `places_new` and swaps it in for the live table in one transaction, so a failure anywhere leaves the live table and `osm_state` as they were. The swap keeps the old table's owner, grants and index names, gives way to searches under a 10 s `lock_timeout` up to `SWAP_ATTEMPTS` times, empties `places_pending` and writes `osm_state` with the day file the daily update resumes after (`resume_sequence`, one day further back than the planet needs, because replaying a change rewrites the same row where a missed one stays wrong). Standard library plus pyosmium and psycopg2 from Debian, with the app's `rules.py` copied in beside it, so `lock_key` and `USER_AGENT` are spelled again here (mirror rows 36 and 37). Validated against Overpass on Washington's extract on 2026-10-18, identical sets and positions. The planet run's time and memory are not measured yet; Washington's took 9.3 s and a container peak of 3,779 MB, most of it `osmium getid -r`. Record: [0184](../docs/decisions/0184-planet-fill-cronjob-and-image.md)
- `fill/Dockerfile` — three stages, built from the repository root because the image carries the app's own `backend/app/services/osm/rules.py` rather than a copy of the rules. `runtime` is Debian trixie-slim pinned by digest, with `apt-get upgrade` and five unpinned packages (osmium-tool, pyosmium and psycopg2 among them, so nothing is compiled), the fixed UID 10001 and the LICENSE, since the image is published on Docker Hub. `test` adds pytest, the app's migrations for the end-to-end database and `services/http.py` for the User-Agent check. `fill` comes last, so a build with no `--target` is the image that ships. `fill/Dockerfile.dockerignore`, which BuildKit reads in place of the root `.dockerignore`, keeps the context to the files the stages copy. `release.yml` pushes it as `zimmertr/bluebird-fill` at the app's version, for amd64 and arm64, and scans it beside the app's image, as the weekly `image-scan.yml` does; `pr.yml`'s Planet Fill job lints it with hadolint, runs the suite and gates on Trivy
- `fill/ruff.toml` — the backend's lint rules (`extend`), read for Python 3.13, the version the image's Debian ships, so pyupgrade never asks for syntax the image cannot parse. `make lint-backend` and CI lint `backend/` and `fill/` together from the repo root
- `fill/tests/` — the suite, run in the image's `test` stage by `make test-fill` against a throwaway PostgreSQL with PostGIS (`backend/tests/db/Dockerfile`) under names unique to the run. `conftest.py` finds `fill.py`, `rules.py`, the migrations and `http.py` in the image or at their places in a checkout, and gives each database test a database of its own, copied from a template the app's migrations built; without `TEST_DATABASE_URL` those skip. `test_fill.py` holds the pure parts: the two mirrors, the candidate filters as a superset over every combination of the tags the clauses name (so a rule that starts reading a new tag fails here rather than finding nothing), the state file, the MD5, the resumed download and the centre pass. `fixture_planet.py` is a hand-written planet around Index, Washington: every kind the rules keep, the features they must not, the shapes the centre pass must survive (a lake in two halves, areas two levels above their crags, a loop of areas), and `EXPECTED`, worked out by hand. `test_e2e.py` runs the fill on it as the CronJob does, from file URLs, and checks the rows, the swapped table's names and grants, a rerun that downloads nothing, `FORCE_FILL` and a rules change refilling, and that a failed download, a swap that fails part way, a held lock and a missing schema each leave `places` as it was
